## 0. 한 장 요약

PM 명세 "실 상태 표현"이 나왔습니다. 위젯 상단에 **커플의 감정 상태를 한 줄로 상시 표시**하는
기능이고, 규격서 11장이 비워 둔 `emotionAnalyses` 가 정확히 그 자리라 **규격을 바꾸지 않고
채웁니다.** 새 `resultType` 도, 요청 필드 추가도 없습니다.

**서버 쪽에서 확인이 필요한 것은 3가지입니다.**

| | 항목 | 성격 |
| --- | --- | --- |
| 🔴 A | **`SKIPPED` 를 보고 전송을 건너뛰고 계신지** | 그러면 새 기능이 화면에 영영 안 뜹니다 |
| 🔴 B | **`emotionAnalyses` 도 수신자별로 갈라서 전송** | 안 가르면 A 화면에 B 것이 뜹니다 |
| 🟢 C | **규격서** 11장 "추후 확정" 칸을 아래처럼 채웠습니다 | 통보. enum 검증 반려 방지 |

A·B 는 **필드가 아니라 동작**이라 규격서만 봐서는 드러나지 않습니다. 그래서 따로 적었습니다.

그 외에 **지금 결정하실 필요 없는 검토 항목이 하나** 있습니다 (7장) — ①번 줄이 데이트
코스 검색을 기다리느라 늦게 뜨는 구조인데, 나중에 실시간성이 요구되면 꺼내면 됩니다.

## 1. 무엇이 생겼나

위젯이 두 줄이고, 응답의 배열도 두 개입니다.

```
┌───────────────────────────────────┐
│  ① 감정이 올라와요                  │  ← emotionAnalyses · 상시. 비지 않는다
│  ② 카카포가 추천하는 장소를 …        │  ← results · 3종 미발동이면 빈 줄
├───────────────────────────────────┤
│  A: 왜 연락을 안 했어?              │
└───────────────────────────────────┘
```

| | 배열 | 발동 | 미발동일 때 |
| --- | --- | --- | --- |
| ① 실 상태 표현 | `emotionAnalyses` | **트리거 없음 · 상시** | 없음 — 항상 채워집니다 |
| ② 개입 3종 | `results` | 트리거 충족 시 | 빈 배열 (지금까지와 동일) |

**두 줄은 자리를 다투지 않습니다.** 3종이 전부 미발동이어도 ①은 그대로 나갑니다.

## 2. 실제 응답 예시

워커가 지금 내보내고 있는 값 그대로입니다 (`case11_mixed` 픽스처).

```json
{
  "analysisRequestId": "…",
  "status": "COMPLETED",
  "results": [ { "resultType": "TONE_CORRECTION", "…": "…" } ],
  "emotionAnalyses": [
    {
      "subjectParticipant": "USER_A",
      "viewerParticipant": "USER_B",
      "emotionType": "ESCALATED",
      "intensityValue": 3.0,
      "shouldShow": true,
      "triggerMessageIds": [206, 208],
      "expiresAt": "2026-08-16T01:37:00+09:00",
      "stateText": "감정이 올라와요"
    },
    {
      "subjectParticipant": "USER_B",
      "viewerParticipant": "USER_A",
      "emotionType": "STABLE",
      "intensityValue": 0.0,
      "shouldShow": true,
      "triggerMessageIds": [205, 207],
      "expiresAt": "2026-08-16T01:37:00+09:00",
      "stateText": "평온해요"
    }
  ]
}
```

**항목이 2개인 이유**: A 화면용 1건, B 화면용 1건입니다. `subjectParticipant`(감정의 주인)와
`viewerParticipant`(보는 사람)가 서로 다릅니다 — **각자 상대방의 상태를 봅니다.**
그래서 두 항목의 내용이 다른 게 정상입니다.

## 3. 🟢 C. 필드 정의 — **규격서** 11장 "추후 확정" 칸을 이렇게 채웠습니다

| 필드 | 값 | 설명 |
| --- | --- | --- |
| `subjectParticipant` | `USER_A` / `USER_B` | 감정의 주인 |
| `viewerParticipant` | `USER_A` / `USER_B` | **이 항목을 볼 사람.** 전송 대상 (아래 B) |
| `emotionType` | 아래 **5종** | 상태 라벨 |
| `intensityValue` | `0.0` ~ `5.0` | 그 상태가 얼마나 뚜렷한가 |
| `shouldShow` | `true` / `false` | **이번 요청에서 문구를 갱신할지.** `false` 면 직전 값 유지 |
| `triggerMessageIds` | 요청에 있던 메시지 id | 판정 근거가 된 그 사람의 발화 |
| `expiresAt` | 마지막 메시지 **+3시간** | 지나면 화면에서 내립니다 |
| `stateText` | 10자 이하 문구 | **규격서에 없는 선택 필드** (아래 6장) |

### `emotionType` 5종

```
STABLE   RESOLVED   ACCUMULATED   ENGAGED   ESCALATED
```

| 값 | 뜻 | 화면 문구 |
| --- | --- | --- |
| `STABLE` | 평온 / 기본 | 평온해요 |
| `RESOLVED` | 애정·설렘 — 감정 **풀어짐** | 다정해 보여요 |
| `ACCUMULATED` | 서운함·오해 — 감정 **쌓임** | 서운해 보여요 |
| `ENGAGED` | 들뜸·활기 — 대화 활발 | 신나 보여요 |
| `ESCALATED` | 분노·격앙 — 감정 **격해짐** | 감정이 올라와요 |

> ⚠️ **필드 이름은 `emotionType` 인데 값은 상태 라벨입니다.** 디자인 확정안의 축이 이쪽이고
> 화면 표현(실 모양·글로우)과 1:1 이라 그렇습니다. 서버는 저장만 하시면 되고 해석하실
> 일은 없습니다. `category` enum 때처럼 **응답 검증에서 반려되지 않도록** 미리 알려드립니다.

### `shouldShow` 의 뜻 — 표시 여부가 아니라 **갱신 여부**입니다

명세상 이 줄은 **항상 화면에 떠 있어야 합니다**(null 처리 예외). 그런데 상대가 아무 말도
안 한 요청에서는 판단할 근거가 없고, 근거 없이 감정을 지어내면 없던 갈등을 만듭니다.

| 값 | 뜻 |
| --- | --- |
| `true` | 새 값입니다. 갱신해 주세요 |
| `false` | **근거가 없어 판단하지 않았습니다. 직전 값을 그대로 두세요** (화면을 비우는 게 아닙니다) |

## 4. 🔴 A. `SKIPPED` 가 사실상 사라집니다

규격서 12장이 `COMPLETED` 를 **"기능 결과 또는 감정 분석 결과가 존재"** 로 정의하고 있고,
이 기능이 상시 작동이라 `emotionAnalyses` 가 매번 찹니다.

| | 전 | 후 |
| --- | --- | --- |
| 3종 미발동 | `SKIPPED` | **`COMPLETED`** (`results: []` + `emotionAnalyses: [2건]`) |
| `SKIPPED` 가 나오는 때 | 개입이 없을 때 | **감정 산출까지 실패했을 때만** |

**`SKIPPED` 를 "아무것도 안 함"으로 보고 전송을 건너뛰고 계시면 상단 한 줄이 영영 안 뜹니다.**
지금까지 `results` 만 보고 계셨다면 `emotionAnalyses` 도 함께 전달되도록 확인 부탁드립니다.

필드가 아니라 동작 변경이라 규격서 대조만으로는 안 드러납니다. 이게 이 문서에서 가장
놓치기 쉬운 항목입니다.

---

## 5. 🔴 B. `emotionAnalyses` 도 수신자별로 갈라서 보내야 합니다

`results` 의 `INDIVIDUAL` 을 `targetParticipant` 로 가르시는 것과 같은 규칙인데,
**가르는 키가 다릅니다.**

| 배열 | 가르는 키 |
| --- | --- |
| `results` | `visibilityType` + `targetParticipant` |
| `emotionAnalyses` | **`viewerParticipant`** |

```
USER_A 에게 보낼 것 → viewerParticipant == "USER_A" 인 항목 1건
USER_B 에게 보낼 것 → viewerParticipant == "USER_B" 인 항목 1건
```

방 단위로 브로드캐스트하면 **A 화면에 B 것까지 두 줄이 뜹니다.** 위 예시로 말하면
A 는 "감정이 올라와요"(자기 자신의 상태)를 보게 되는데, 이 기능은 **상대방의 상태를
보여주는 것**이라 의미가 통째로 뒤집힙니다.

---

## 6. 🟢 선택 필드 `stateText` — 안 받으셔도 됩니다

화면에 나가는 문구(10자 이하)를 담을 자리가 규격서 11장에 없어서 워커가 **선택 필드**로 실어
보내고 있습니다. 저장이 필요 없으시면 그냥 무시하시면 됩니다.

프론트가 `emotionType` → 문구 매핑을 직접 갖는 방식으로 가도 됩니다 (3장 표가 그 매핑이고,
라벨당 문구가 1개로 고정이라 분기가 없습니다). **어느 쪽이든 워커 로직은 같습니다.**

컬럼을 하나 두실 수 있다면 그쪽을 권합니다 — 문구가 바뀔 때 프론트 배포 없이 워커에서
바꿀 수 있고, 나중에 로그 분석에도 남습니다.

## 7. 🔵 검토 요청 — ①번 줄을 먼저 내보낼 수 있습니다

**지금 당장 필요한 건 아닙니다.** 규격서 4장에 "AI 처리 시간이 길어 비동기 콜백이 필요할
경우 별도 협의"가 있어서, 선택지만 정리해 둡니다.

### 문제 — ①번 줄이 ②번 줄을 기다립니다

동기 단일 응답이라 **①번 줄은 4초면 확정되는데 데이트 코스 검색이 끝날 때까지 같이
기다립니다.**

| 요청 | 총 소요 | ①번 줄이 확정되는 시점 |
| --- | --- | --- |
| 개입 없음 | 3.6s | 3.6s |
| 말투 교정 발동 | 5.6s | **4.0s** |
| 데이트 코스 발동 | 9.5s | **4.0s** |
| 데이트 + 콜드 스타트 | 11.3s | **4.0s** |

①번 줄은 "실시간 감정 상태"인데 데이트 코스 때문에 9.5초 뒤에 뜨는 구조입니다.
②번 줄은 원래 즉시성이 요구되는 기능이 아니라 괜찮습니다.

### 선택지

| | 방식 | 서버 작업 | 워커 작업 |
| --- | --- | --- | --- |
| **(a)** | 그대로 둔다 | 없음 | 없음 |
| **(b)** | 서버가 **두 번 호출** — 상태 전용 + 전체 | 호출 1회 추가 | 엔드포인트 1개 추가 |
| **(c)** | 워커가 ②번 줄을 **비동기 콜백**으로 밀어준다 | **콜백 수신 엔드포인트 신설** | 콜백 발신 |

**(b)를 제안합니다.** (c)는 서버에 새 엔드포인트와 재시도·순서 보장이 생겨서 이 단계에
비해 큽니다. (b)는 기존 요청 형식을 그대로 쓰고 응답에서 `results` 만 비면 됩니다.

```
POST /internal/v1/chat-analyses/state   → 약 4초, emotionAnalyses 만
POST /internal/v1/chat-analyses          → 지금 그대로 (전체)
```

**비용**: 대화 분절이 두 번 돌아 LLM 호출이 요청당 1회(약 1.8초·입력 1,500 토큰) 늘어납니다.
지연을 토큰으로 사는 셈입니다.

### 저희 의견

**타임아웃이 30초로 정해지고 시연에서 9.5초가 거슬리지 않으면 (a)로 두는 게 맞습니다.**
채팅이 멈추는 게 아니라 위젯이 늦게 갱신되는 것이고, 커플은 그동안 계속 대화합니다.

**①번 줄이 "실시간"으로 느껴져야 한다는 요구가 나오면 그때 (b)로 갑니다.** 워커 쪽은
반나절이면 붙습니다 — `analyze()` 를 상태 단계까지만 도는 함수로 한 번 더 감싸면 됩니다.

## 8. 요청하지 않기로 한 것 (기록만)

검토했다가 뺐습니다. **서버 작업이 필요 없다는 뜻입니다.**

| 항목 | 왜 뺐나 |
| --- | --- |
| 응답 `trend` (쌓임/풀어짐) | 추이가 상태 라벨 안에 이미 있습니다 (`ACCUMULATED` = 쌓임, `RESOLVED` = 풀어짐) |
| 요청 `previousEmotions` (직전 감정값) | 있으면 요청 경계를 넘는 추이가 정확해지지만, 없어도 요청에 들어온 스트림 안에서 판단됩니다. **정확도 문제지 구현 가능 여부가 아닙니다** |

9장의 `recentResults` · `speakerProfiles` 는 **없으면 규칙 자체가 구현 불가**라
성격이 달랐고, 그래서 요청드렸습니다 (합의 완료).

두 요청 필드는 **선택**이라 서버가 안 보내도 지금처럼 동작하고, 보내주시면 그 값을
우선합니다. **한쪽만 배포해도 안 깨집니다.**

### 타임아웃 — 15초도 들어갑니다

이전에 "15초로 잡으셔야 한다면 병렬화가 필요합니다"라고 드렸는데 **그 병렬화를 먼저
해뒀습니다.** 분절 이후 독립인 단계를 동시에 돌립니다 (결과·호출 횟수는 동일).
실측은 7장 표와 같습니다 — 최악이 11.3초입니다.

**30초면 넉넉하고 15초도 됩니다.** 어느 쪽으로 정하셔도 됩니다.

## 10. 확인 부탁드릴 것 — 체크리스트

**꼭 필요한 것**

- [ ] **`SKIPPED` 처리** — 전송을 건너뛰는 로직이 있는지. 있다면 `emotionAnalyses` 도 보도록 (4장)
- [ ] **수신자별 분리 전송** — `emotionAnalyses` 를 `viewerParticipant` 로 가르기 (5장)
- [ ] **`emotionType` 5종 · `intensityValue` 0~5 · `expiresAt`** 저장·검증에 문제 없는지 (3장)

**정해주시면 되는 것**

- [ ] 타임아웃 (30초 / 15초 둘 다 가능) + 1회 요청 메시지 개수 (9장)
- [ ] `stateText` 선택 필드를 받으실지 (6장)

**나중에 필요해지면**

- [ ] ①번 줄을 먼저 내보내는 2단계 호출 (7장) — **지금은 (a) 그대로 두기를 권합니다**

설계 근거와 판정 로직 전문은 `docs/state-display-v4.md` 에 있습니다.
워커는 이미 위 응답을 내보내고 있어서, 서버 쪽 준비가 되면 바로 붙습니다.
