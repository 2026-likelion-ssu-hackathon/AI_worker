## 1. 명세 원문

| 항목 | 내용 |
| --- | --- |
| 대상 | 전체 (커플 양측 동일 노출) |
| 기능 성격 | 관계 어시스턴트 |
| 개입 갈래 | 정보 전달 (상태 표현) |

### 사용자 스토리

**[전체]** 상대방과 대화를 나누는 중, 카카포가 상단에 상대방의 현재 감정·관계 상태를
한 줄로 보여준다.

**[개별]** 말투는 평범한데 상대가 서운해하는 것 같다. 카카포가 "서운해 보여요" 같은
문구로 상태를 알려주고, 사용자는 이를 참고해 대화 톤을 조절한다.

### 기능 설명

현재 대화 스트림을 기반으로 **감정 상태 + 관계 상태를 추출**해 상단 한 줄 문구로 제시한다.

감정 수치(예: Sadness 3점)를 산출하고, 이를 **감정이 쌓임 / 풀어짐 / 슬퍼함** 등의
상태 표현으로 변환해 노출한다.

다른 3개 기능과 달리 **별도 트리거 조건 없이 상시 작동**하며, null 처리 대상이 아니다.

### 기능 플로우

```
[대화 스트림 수신] → [감정·관계 상태 추출 및 수치화] → [상태 라벨링]
→ [표현 문구 생성(10자 이하)] → [상단 위젯 노출] → [스트림 갱신 시 재산출]
```

### 트리거 조건

**없음 — 상시 작동.** 스트림 단위로 갱신. 데이트 코스 추천 / 유튜브 추천 / 감정 중재의
트리거 충족 여부와 무관하게 독립 작동.

### 사용하는 이전 기억 대화 내역

- **현재 대화 스트림** (최우선 근거)
- 누적 감정 상태의 변화 추이 (쌓임 → 풀어짐)
- 두 사람의 관계 맥락

### 작동 방식

```
대화 스트림에서 감정 신호 추출
→ 감정 수치 스코어링 (예: Sadness 3점)
→ 특수 상태(격한 감정 등) 판별
→ 상태 라벨 매핑
→ 표현 문구 생성
```

※ 감정 중재 기능은 **감정이 격해질 때** 별도로 작동하는 로직이므로 본 기능과 분리.

### 화면 방식

상단 카카포 **한 줄 문구 영역**

- 문구 길이: **최대 10자 이하**
- 어미: **"~여요 / ~요 / ~해요"** 체
- 예) "서운해 보여요"
- 디자인 컨셉 확정 후 시안 반영

### 제약 사항

대화 스트림은 커플만의 공간이며 침범하지 않는다.
단정·판단형 표현 금지, 문구 10자 초과 불가.

### 예외

나머지 3개 기능은 트리거 미충족 시 **null 처리(문구 미노출)**.
**단, 실 상태 표현은 null 처리 예외 — 항상 문구를 출력한다.**

## 2. 화면 구조 — 위젯은 딱 2줄이다

**PM 확인 (2026-08-17).** 상단 위젯에 뜨는 것은 **두 줄, 그게 전부다.**

```
┌───────────────────────────────────┐
│  ① 서운해 보여요                    │  ← 감정 상태. 상시. 비지 않는다
│  ② 카카포가 추천하는 장소를 …        │  ← 3종. 미발동이면 null (빈 줄)
├───────────────────────────────────┤
│  A: 오늘 뭐했어?                    │
│  B: 그냥 집에 있었어                 │  ← 커플만의 공간
└───────────────────────────────────┘
```

| | 줄 | 내용 | 미발동 시 |
| --- | --- | --- | --- |
| ① | 감정 상태 | 이 문서의 기능. 10자 이하 | **없음 — 항상 찬다** |
| ② | 개입 | 데이트 코스 / 유튜브 / 말투 교정 | **`null` — 빈 줄** |

**이 구조가 이 문서의 설계 대부분을 결정한다.**

- **두 줄은 자리를 다투지 않는다.** 3종이 전부 미발동이어도 ②만 비고 ①은 그대로다 →
  5장의 배열 분리(`emotionAnalyses` / `results`)가 화면과 1:1로 맞는다
- **"비어 있음"의 의미가 줄마다 다르다.** ②의 빈 줄은 정상 상태(`SKIPPED` 의 화면)고,
  ①의 빈 줄은 **있으면 안 되는 상태**다
- **①은 글자다.** 워커가 내보내는 10자가 그대로 화면 한 줄이 된다. 그래서 문구의 안전을
  워커가 끝까지 책임져야 한다 (3장·6장)

> **"사랑끈"은 ①번 줄의 시각 컨셉이다.** 별도의 그림 영역이 아니라 이 한 줄을 어떻게
> 보여줄지의 문제다. **디자인 확정 (2026-08-17)** — 상태 라벨 5종마다 실 모양과 글로우가
> 정해졌다 (6장 표). 워커는 라벨과 강도(`emotionType`·`intensityValue`)를 실어 보내고,
> 그걸로 무엇을 그릴지는 그 표가 정한다 (3-2).

### 기존 3종과 다른 점

기존 3종을 만들 때 세운 전제가 여기서는 전부 뒤집힌다. 같은 틀에 넣으면 안 된다.

| | 기존 3종 | 실 상태 표현 |
| --- | --- | --- |
| 발동 | 게이트 통과 시에만 | **상시** |
| 기본값 | **침묵** — 애매하면 개입하지 않는다 | 항상 무언가 뜬다 |
| 화면 자리 | **②번 줄** (셋이 한 자리를 나눠 쓴다) | **①번 줄** (독점) |
| 노출 단위 | 결과 1건을 누구에게 보일지 | **보는 사람마다 내용이 다르다** |
| 출력 길이 | 문장 | **10자** |
| LLM 비용 | 게이트가 걸린 요청만 | **매 요청 고정 비용** |

> ### 워커 노트 — "침묵이 기본값"이 여기서는 성립하지 않는다
>
> 지금까지 이 워커의 안전장치는 전부 **안 내보내는 것**이었다. 유튜브는 후보 전원이
> 부적합하면 침묵하고, 데이트 코스는 카카오 결과가 부족하면 미발동하고, 말투 교정은
> 금지어에 걸리면 재생성 1회 후 버린다. **이 기능에는 그 손잡이가 없다.**
> 명세가 "null 처리 예외 — 항상 출력"으로 못박았기 때문이다.
>
> 그래서 안전은 **출력 단계가 아니라 설계 단계에서 미리 확보해야 한다.**
> 6장(문구를 사전에서 고른다)과 7장(중립을 기본 라벨로 둔다)이 그 대응이다.

## 3. 절대 제약과의 충돌 — 가장 먼저 정리해야 할 것

`CLAUDE.md` 의 절대 제약은 이 프로젝트의 핵심 가치다.

> **관계 상태를 언급하는 문구를 절대 출력하지 않는다.**
> 내가 눈치채기 전에 kakapo가 먼저 눈치채고 조용히 회복시킨다.

그런데 이 명세의 첫 문장은 **"감정 상태, 관계를 진단하고"** 다. 그대로 읽으면
"관계를 진단해서 화면에 상시로 띄운다"가 되고, 이건 절대 제약과 정면으로 부딪힌다.

### 3-1. 걸리는 것과 걸리지 않는 것

`CLAUDE.md` 는 이미 이 경계를 정의해 뒀다. **금지 대상은 관계를 규정하는 말이지
감정을 언급하는 것 전부가 아니다.**

| | 예시 | 이 기능에서 |
| --- | --- | --- |
| ✅ 감정 알아봄 | "서운해 보여요", "편안해 보여요" | **이게 기능이다** |
| ❌ 관계 규정 | "사이가 팽팽해요", "요즘 뜸해요", "권태기" | 출력 금지 |
| ❌ 사람 평가 | "예민하시네요", "무뚝뚝해요" | 출력 금지 |

명세의 대표 예시 **"서운해 보여요"는 감정 알아봄이라 통과한다.** 이 기능의 출력을
전부 이 성격으로 맞추면 절대 제약과 충돌하지 않는다.

### 3-2. "사랑끈이 팽팽해집니다"는 문구가 아니라 시각 컨셉으로 본다

원문의 `ex) 커플 싸울 때 → (가제) 사랑끈이 팽팽해집니다` 는 **문구 규격 세 가지를
동시에 어긴다.**

| | 규격 | "사랑끈이 팽팽해집니다" |
| --- | --- | --- |
| 길이 | 10자 이하 | 11자 |
| 어미 | ~여요 / ~요 / ~해요 | ~니다 |
| 대상 | (3-1 표) | **두 사람의 관계**를 서술한다 |

같은 명세 표에 "디자인 컨셉 확정 후 시안 반영"이 적혀 있고 문구에는 `(가제)` 가 붙어 있다.
**문장이 아니라 컨셉 스케치로 읽는 게 맞다고 봤다.**

> ### 워커 노트 — 그림은 남고, 그림에 붙는 글자는 안 된다
>
> **①번 줄이 상시로 뜨는 것은 확정이다** (2장). 워커가 정할 문제가 아니라 이미 정해진
> 화면이다. 남은 문제는 그 줄을 **무엇으로 보여주는가**다 — 여기서 워커가 지킬 선은
> 하나다. **그림에 글자를 붙이지 않는다.**
>
> "권태기예요"라는 문장은 사용자 머릿속에 그 단어를 심지만, 팽팽해진 실 그림은
> 단어를 주지 않는다. 절대 제약의 근거가 "그 말을 들으면 의식이 심해진다"이므로
> 그림과 문장은 위험도가 다르다. 다만 실 옆에 "팽팽함" 같은 라벨이 붙는 순간
> 그림이 문장이 되고 제약이 그대로 깨진다.
>
> 그래서 워커가 내보내는 것을 이렇게 갈랐다.
>
> | | 워커가 내보내는 것 | 소유 |
> | --- | --- | --- |
> | ①번 줄의 글자 | 10자 문구. **상대방의 감정**까지만, 관계를 서술하지 않는다 | 워커 (하드 검증) |
> | ①번 줄의 생김새 | `emotionType`(라벨 5종) · `intensityValue` — **값만** | 프론트·디자인 |
>
> **워커는 그 수치에 이름을 붙여 내보내지 않는다.** 상태명·단계명·게이지 라벨 전부
> 해당한다. 필요해 보이면 만들지 말고 11장에 올린다.

### 3-3. 상시 노출은 위반 확률을 곱한다

말투 교정은 게이트가 걸린 요청에서만 문장을 만든다. 이 기능은 **매 요청 만든다.**
위반 확률이 1000분의 1이어도 하루 수백 번 뜨는 자리라면 반드시 나온다.
**"프롬프트로 잘 막으면 된다"가 성립하지 않는 자리다.** 6장의 근거다.

### 3-4. 하드 필터의 사각지대 — 지금 구조로는 검사되지 않는다

`worker/filter.py` 의 `visible_texts()` 는 **`AiResult` 의 `resultData` 만** 본다.

```python
def visible_texts(result: AiResult) -> list[str]:
    data = result.result_data
    if isinstance(data, ToneResultData): ...
```

이 기능의 문구를 `emotionAnalyses` 에 실으면 **하드 필터를 그냥 통과한다.**
`CLAUDE.md` 가 세그먼테이션에서 화제 라벨을 안 만든 이유와 정확히 같은 함정이다 —
"`filter.py` 는 `AiResult` 의 화면 문자열만 검사해서 안 걸러진다."

**필터 확장은 이 기능의 선택 사항이 아니라 전제 조건이다** (10장).

## 4. 명세 내부 충돌 3건과 처리

### ① "커플 양측 동일 노출" vs "상대방의 상태"

대상 칸은 **전체 (커플 양측 동일 노출)** 인데, 사용자 스토리는 **"상대방의 현재 감정"**
을 보여준다고 한다. 상대방 기준이면 A 화면과 B 화면의 **내용이 다르다.**

**"동일 노출"이 아니라 "대칭 노출"로 해석했다.** 양쪽 다 한 줄이 뜨고, 각자 상대의 상태를
본다. 근거 두 가지:

- 기능 부제가 **"상대방 감정 showing"** 이다. 내 감정을 나에게 보여주는 건 기능이 아니다
- 규격서 11장이 `subjectParticipant`(감정의 주인)와 `viewerParticipant`(보는 사람)를
  **따로** 두고 있다. 두 값이 같을 필요가 없게 설계된 자리다

```
A 화면 상단  "서운해 보여요"      ← subject=USER_B, viewer=USER_A
B 화면 상단  "편안해 보여요"      ← subject=USER_A, viewer=USER_B
```

이건 `CLAUDE.md` 의 "위젯은 사람마다 다르게 보인다"와도 맞는다. 다만 **`INDIVIDUAL`
카드와 성격이 다르다** — 개별 카드는 상대가 그런 게 떴다는 사실 자체를 몰라야 하지만,
이 한 줄은 양쪽 다 하나씩 갖는다. 숨기는 게 아니라 각자 다른 것을 본다.

### ② "누적 추이" vs 무상태 REST

명세는 **"누적 감정 상태의 변화 추이 (쌓임 → 풀어짐)"** 를 요구한다. 그런데 워커는
동기 REST 요청마다 상태가 없고, 요청 페이로드에 과거 감정값이 들어오지 않는다.
`docs/contract-review.md` 의 `recentResults` · `speakerProfiles` 와 **똑같은 문제**다.

- **MVP** — 요청에 들어온 스트림 안에서만 추이를 본다. 활성 세그먼트와 그 직전 맥락을
  함께 넣고 "쌓이는 중 / 풀리는 중 / 그대로"를 묻는다. 요청 경계를 넘는 추이는 못 본다
- **정식** — 서버가 직전 감정값을 요청에 실어준다 (9장, 규격 변경 요청 3번)

### ③ "감정 중재와 분리" vs 이미 있는 감정 판정

명세는 감정 중재와 본 기능을 분리하라고 못박았다. 그런데 `worker/tone.py` 의
`ToneJudgeLLMOutput` 은 이미 `emotion: calm / irritated / angry / hurt` 를 산출한다.
재사용하고 싶어지지만 **재사용하면 안 된다.**

| | 말투 교정의 emotion | 실 상태 표현 |
| --- | --- | --- |
| 언제 | 룰 게이트가 걸린 요청에만 | 매 요청 |
| 누구 | 문제 표현을 **보낸 사람** 1명 | **두 사람 각각** |
| 왜 | 대체 문장을 쓰기 위한 재료 | 그 자체가 출력 |

**사용자 스토리 [개별]이 이 분리를 그대로 설명한다** — "말투는 평범한데 상대가 서운해하는
것 같다". 말투 게이트가 안 걸리는 구간이 정확히 이 기능의 자리다.
게이트에 종속시키면 명세가 원하는 케이스가 통째로 사라진다.

## 5. 어디로 내보낼 것인가 — `emotionAnalyses` 다

두 가지 길이 있다. **규격서 11장 `emotionAnalyses` 를 채우는 쪽으로 결정했다.**

| | 4번째 `resultType` 신설 | **`emotionAnalyses` 채우기 (채택)** |
| --- | --- | --- |
| 규격 변경 | `resultType` enum + `resultData` 구조 신설 | **필드 2개 추가** |
| 화면 자리 | `results` 배열 = **②번 줄**과 섞인다 | 별도 배열 = **①번 줄과 1:1** |
| 대상 표현 | `visibilityType` 로는 대칭 노출을 못 쓴다 | `subject`/`viewer` 가 이미 있다 |
| 서버 역할 | 새로 정의 | 2장에 이미 있다 — "감정 분석 결과 생성/저장" |
| 상시성 | 카드 3종과 같은 배열에 섞여 우선순위가 꼬인다 | 분리돼 있어 안 꼬인다 |

**화면이 두 줄이면 배열도 두 개인 게 맞다.** `results` 는 ②번 줄, `emotionAnalyses` 는
①번 줄이다. 한 배열에 섞으면 프론트가 매번 `resultType` 을 보고 어느 줄인지 갈라야 하고,
"②는 비었는데 ①은 차 있다"는 정상 상태를 표현하기 어려워진다.

**규격서는 이 기능의 자리를 이미 비워 두고 있었다.** 11장 예시가 그대로 이 명세다.

```json
{
  "subjectParticipant": "USER_A",
  "viewerParticipant": "USER_B",
  "emotionType": "ANGER",
  "intensityValue": 4.0,
  "shouldShow": true,
  "triggerMessageIds": [101],
  "expiresAt": null
}
```

`emotionType` + `intensityValue` 가 명세의 "감정 수치 스코어링(Sadness 3점)"이고,
`subject`/`viewer` 가 4장①의 대칭 노출이다. **`docs/contract-review.md` 에서 "명세가
아직 없어 `[]` 로 보낸다"고 답한 그 배열이 이 문서로 채워진다.**

### 모자란 것 — 화면 문구를 실을 자리가 없다

11장에는 **문구 필드가 없다.** 산출된 라벨을 문장으로 바꾼 결과를 담을 곳이 필요하다.
필드를 추가하지 않으면 프론트가 `emotionType` → 문구 매핑을 직접 들고 있어야 하는데,
그러면 **절대 제약을 지키는 문자열의 소유가 워커 밖으로 나간다.** 하드 필터가 검사할 수
없는 자리에 화면 문구가 생긴다 (3-4). 그래서 워커가 실어 보내는 쪽을 제안한다.

→ 규격 변경 요청 4건은 9장.

## 6. 문구를 누가 쓰는가 — LLM 이 아니라 고정 사전

**LLM 은 감정 점수까지만 낸다. 라벨은 룰이, 화면 10자는 사전이 정한다.**

이건 이 레포에서 이미 두 번 쓴 패턴이다.

| 기능 | LLM 이 하는 것 | LLM 이 하지 않는 것 |
| --- | --- | --- |
| 대화 분절 | 발화별 연속성 **점수** | 경계 결정 — 룰 임계값이 한다 |
| 데이트 코스 | 검색어·추천 이유 | 상호명·링크 — 카카오가 준 것만 쓴다 |
| **실 상태 표현** | **감정 4축 점수 (0~5)** | **라벨 — 임계값이 정한다 / 문구 — 사전에서 고른다** |

근거:

- **위반 확률이 곱해지는 자리다** (3-3). 상시 노출에서 자유 생성은 절대 제약을 상시로
  노출시킨다. 사전이면 위반 확률이 **0** 이다 — 문자열이 유한하고 미리 검사할 수 있다
- **10자와 어미 제약을 구조적으로 보장한다.** 생성이면 매번 세고 잘라야 하는데,
  10자를 자르면 문장이 깨진다
- **문구의 주인은 PM·디자인이다.** `worker/copy.py` 주석이 이미 그렇게 적고 있다.
  "디자인 컨셉 확정 후 시안 반영"이면 사전만 교체하면 되고 프롬프트를 다시 쓸 일이 없다
- **결정적이다.** 같은 대화에 항상 같은 문구가 나온다. 시연에서 재현된다
- **싸다.** 출력 토큰이 라벨 몇 개로 줄어 상시 호출의 비용이 내려간다

단점은 표현 다양성이다. 라벨당 문구를 2~3개 두고 `messageId` 기준으로 결정적으로
고르면 완화된다 (무작위는 쓰지 않는다 — 재현이 깨진다).

### 문구 사전 — 5종 확정 (디자인, 2026-08-17)

**감정 5종과 실 모양·글로우가 확정됐다.** 워커는 이 표의 `상태 라벨` 하나를 고르는 일만 한다.

| 상태 라벨 | 감정 | 실 모양 | 글로우 | 문구 | 자수 |
| --- | --- | --- | --- | --- | --- |
| `STABLE` | 평온 / 기본 | 아래로 축 늘어진 곡선 | 없음 (무채색) | 평온해요 | 4 |
| `RESOLVED` | 애정 / 설렘 | 중앙에 하트 매듭 | 핑크·마젠타 | 다정해 보여요 | 7 |
| `ACCUMULATED` | 서운함 / 오해 | 중앙이 엉킨 매듭 | 파랑 | 서운해 보여요 | 7 |
| `ENGAGED` | 들뜸 / 활기 | 크고 규칙적인 파동 | 초록 | 신나 보여요 | 6 |
| `ESCALATED` | 분노 / 격앙 | 날카롭고 좁은 스파이크 | 빨강 | 감정이 올라와요 | 8 |

> ### 워커 노트 — 확정안이 설계를 한 단계 단순하게 만들었다
>
> 초안은 **감정 7종 × 추이 3종**의 격자였다. 확정안은 그 두 축이 **하나로 합쳐져 있다** —
> `RESOLVED`(풀어짐) · `ACCUMULATED`(쌓임) · `ESCALATED`(격해짐)가 추이를 라벨 안에
> 이미 담고 있다. 그래서:
>
> - **`trend` 필드가 통째로 사라진다.** 9장에서 뺐던 판단이 확정안으로 확인됐다
> - **사전이 5줄이다.** 초안 13줄에서 줄었고, 5종 전부 실 모양과 1:1이라 화면과 안 어긋난다
>
> `ANXIETY`(불안·걱정)는 확정안에 없다. 5종에 접어 넣는다 — 관계 맥락의 걱정은
> `ACCUMULATED`, 그 외에는 `STABLE`. **없는 라벨을 워커가 만들지 않는다.**

### 라벨은 LLM 이 고르지 않는다 — 감정 점수에서 룰이 정한다

**처음에는 LLM 에게 라벨 5종 중 하나를 직접 고르게 했다. 실측에서 깨졌다** (12장).

`case11_mixed` 에서 **말투 교정은 공격 표현(`generalization`)으로 잡은 발화를, 상태 산출은
서운함(`ACCUMULATED`)으로 읽었다.** 3회 반복에서 전부 그랬다. 한 발화를 두 기능이 다르게
읽는 것이고, **라벨이 LLM 안에 있으니 조정할 손잡이가 없었다** — 프롬프트를 다시 쓰는 것
말고 할 수 있는 게 없다.

**분절에서 경계를 LLM 밖으로 뺀 이유와 똑같다.** 명세의 산출 흐름도 원래 이쪽이다 —
"감정 수치 스코어링(예: Sadness 3점) → 상태 라벨 매핑".

```
LLM     화자마다 감정 4축 점수      애정 0~5 · 서운 0~5 · 활기 0~5 · 분노 0~5
  ↓
룰      pick_label()               임계값으로 라벨 1개
  ↓
사전    copy.STATE_TEXT            문구 10자
```

| 축 | 라벨 | |
| --- | --- | --- |
| `affection` | `RESOLVED` | 쌓인 것이 **풀리는** 흐름 |
| `hurt` | `ACCUMULATED` | 안으로 **쌓이는** 흐름 |
| `joy` | `ENGAGED` | |
| `anger` | `ESCALATED` | 밖으로 **터뜨림** |
| *(없음)* | `STABLE` | 네 축이 전부 임계 아래 |

**`STABLE` 에 해당하는 축을 두지 않는다.** 처음엔 `calm` 축을 뒀는데 모델이 그걸
바닥값으로 깔아서(전 픽스처에서 3점) 다른 축이 3 이하면 전부 `STABLE` 로 먹혔다.
평온은 다른 감정이 없는 상태지 경쟁하는 감정이 아니다.

임계값 세 개가 손잡이다.

| 상수 | 값 | 뜻 |
| --- | --- | --- |
| `MIN_SCORE` | 3 | 최고점이 이 아래면 `STABLE`. **프롬프트 앵커("3 = 뚜렷하다")에 맞췄다** |
| `ANGER_WINS` | 3 | `anger` 가 이 이상이면 다른 축보다 낮아도 `ESCALATED` |
| `PRIORITY` | anger→hurt→joy→affection | 동점일 때의 순서 |

**`ANGER_WINS` 가 `case11` 을 고친 값이다.** 분노는 혼자 오지 않는다 — 서운해서 화가
난다. 그래서 다투는 구간은 `hurt` 와 `anger` 가 같이 높고, 최고점만 보면 서운함이 이겨서
파란 매듭이 뜬다. 화면에 필요한 건 "지금 격해졌다"는 신호고 그게 빨간 스파이크의 자리다.
**보수적으로 가려면 이 값을 올리면 된다 — 프롬프트를 고칠 필요가 없다.**

`PRIORITY` 에서 `joy` 를 `affection` 보다 앞에 둔 이유: `RESOLVED`(감정 풀어짐)는 쌓인
것이 있었을 때만 뜻이 있는 라벨이다. 데이트 계획처럼 애정과 활기가 같이 높은 자리에서
"다정해 보여요"가 뜨면 화해한 것처럼 읽힌다 (`case9_date` 가 실제로 그랬다).

#### `ESCALATED` 문구 교체 기록 (2026-08-17 확정)

최초 확정안은 **"많이 화났어요"** 였고, 검토 중 **"감정이 올라와요"** 로 바꿨다.
5개 중 이것만 명세 자체의 제약과 부딪혔기 때문이다.

| | |
| --- | --- |
| 명세 제약 | "**단정·판단형 표현 금지**" |
| 최초 문구 | "많이 화났어요" — 5개 중 유일한 **단정형**, 강도를 말로 키운다 |
| 확정 문구 | "감정이 올라와요" — 추측·관찰형. `CLAUDE.md` 의 허용 예시를 줄인 것 |

`ESCALATED` 가 뜨는 순간은 대개 **말투 교정이 같이 발동하는 순간**이다. A 화면 ②줄에는
교정 제안이 뜨고, B 화면 ①줄에는 상태 문구가 뜬다. 여기서 "화가 났다"고 단정해서 상대에게
알려주면 B 는 방어적으로 반응하고 **개입이 갈등을 키우는 방향으로 돈다.**
나머지 4개는 확정안 그대로 쓴다.

> 문구를 지을 때 **글자 수를 먼저 센다.** "화가 많이 났나 봐요"처럼 자연스러운 표현이
> 11자로 규격을 넘는다. 5개 전부 10자 이하·`~요` 체·`filter.BANNED` 미포함을 검산했다.

**문구만 정해 주시면 됩니다.** 워커 쪽 로직은 어느 쪽이든 동일합니다.

문구 작성 규칙 (사전을 늘릴 때 지킬 것):

1. **주어는 상대방의 감정이다.** 두 사람의 관계가 주어가 되면 안 된다 (3-1)
2. **사람을 평가하지 않는다.** "예민해요"(X) / "감정이 올라와요"(O). 말투 교정의
   "대상이 사람이면 안 되고 말이면 된다"와 같은 원칙이다
3. **추측 표지를 쓴다.** `~보여요` · `~나 봐요`. 명세의 "단정·판단형 표현 금지"다.
   틀렸을 때 "아닌데?"로 넘길 수 있는 문장이어야 한다
4. **강도에 비례해 세지지 않는다.** 강도 5라고 "많이 화났어요"로 올리지 않는다 —
   격한 순간에 상대의 화를 크게 알려주면 갈등을 키운다. 강도는 수치로만 나간다
5. 10자 이하 · `~여요 / ~요 / ~해요` 체

> ### 워커 노트 — 사전을 임포트 시점에 검증한다
>
> 문구가 상수라는 것은 **미리 전부 검사할 수 있다**는 뜻이다. `copy.py` 로드 시점에
> 사전 전체를 훑어 ① 10자 이하 ② 어미 화이트리스트 ③ `filter.BANNED` 미포함을 확인한다.
> PM 이 문구를 바꿔도 규격 위반이면 그 자리에서 터진다. 화면에 나간 뒤에 발견하지 않는다.

## 7. 산출 파이프라인

```
활성 세그먼트(ctx.active) + 직전 맥락
   ↓
state.read_state()          LLM 1회 — 화자별 감정 4축 점수 (라벨도 문구도 없음)
   ↓
state.pick_label()          룰 — 임계값으로 라벨 1개 + 강도
   ↓
룰 — 근거 검증               해당 화자의 발화가 없으면 중립 유지 (shouldShow=false)
   ↓
copy.STATE_TEXT[라벨]        문구 선택 (LLM 아님)
   ↓
emotionAnalyses[]           viewer 별 1건씩, 최대 2건
```

### 보는 범위

`CLAUDE.md` 의 "맥락과 트리거를 갈라 쓴다" 표에 한 줄이 추가된다.

| | 보는 범위 |
| --- | --- |
| 게이트 · 트리거 id · RAG · 기억 추출 | `ctx.active` |
| 말투 판정 프롬프트의 직전 대화 | `ctx.context` |
| 말투 기준선 (`profile.py`) | `ctx.messages` |
| **실 상태 표현** | **`ctx.context`** — 활성 세그먼트 + 부족분만 앞에서 채움 |

활성 세그먼트만 보면 **추이를 볼 수 없다.** "쌓임 → 풀어짐"은 최소 두 시점이 필요하다.
말투 판정이 같은 이유로 쓰는 `ctx.context` 를 그대로 쓴다 — 새 범위를 만들지 않는다.

전체 스트림(`ctx.messages`)을 쓰지 않는 이유는 분절 설계 그대로다. 세 시간 전에 끝난
다툼의 감정을 지금 화면에 띄우면 늦은 게 아니라 **틀린 것**이다.

### 중립이 기본값이다

명세는 "항상 출력"이지만, **근거가 없을 때 감정을 지어내면 없던 갈등을 만든다.**
B 가 "ㅇㅇ" 한 마디만 한 요청에서 "서운해 보여요"가 뜨면, A 는 있지도 않은 서운함에
반응하기 시작한다. 데이트 코스가 없는 발화를 인용하지 않는 것과 같은 이유다.

| 상황 | 처리 |
| --- | --- |
| 근거가 충분 | 해당 라벨 + `shouldShow: true` |
| 그 화자의 발화가 활성 맥락에 없음 | `STABLE` + `shouldShow: false` (프론트는 직전 문구 유지) |
| 신호가 약함 / 확신 없음 | `STABLE` — "평온해요" |
| LLM 호출 실패 | 해당 요청은 배열을 비운다. 문구를 지어내지 않는다 |

`shouldShow` 를 **"이번 요청에서 문구를 갱신할지"** 로 정의하면 "항상 화면에 뭔가 떠
있다"(명세)와 "근거 없이 지어내지 않는다"(워커 원칙)를 동시에 만족한다.
화면은 비지 않고, 값은 갱신되지 않는다.

### 값 정의 제안 (규격서 11장 "추후 확정")

| 필드 | 값 |
| --- | --- |
| `emotionType` | `STABLE` `RESOLVED` `ACCUMULATED` `ENGAGED` `ESCALATED` **5종 확정** |
| `intensityValue` | `0.0` ~ `5.0` (명세 "Sadness 3점", 규격서 예시 `4.0` 과 정합) |
| `stateText` *(추가 요청)* | 화면 문구. 10자 이하 |
| `shouldShow` | 위 정의 |
| `triggerMessageIds` | 판정 근거가 된 활성 맥락의 메시지 id |
| `expiresAt` | **마지막 메시지 + 3시간** |

`emotionType` 에 **감정 이름(`Calm`·`Anger`…)이 아니라 상태 라벨을 넣는다.** 디자인 표의
`State Label` 이 이미 대문자 스네이크로 코드값처럼 적혀 있고, 실 모양과 1:1 이라 프론트가
받아서 바로 쓸 수 있는 축이 이쪽이다. 감정 이름 쪽(`Calm / Neutral`)은 슬래시가 들어가
enum 이 되지 않는다. **필드 이름은 `emotionType` 인데 값은 상태 라벨**이라는 어긋남만
서버에 한 줄 설명한다 (9장).

`intensityValue` 는 문구를 세게 만드는 데 쓰지 않는다 (6장 규칙 4). 글로우 세기·파동
진폭·스파이크 날카로움처럼 **실의 강약**에만 쓰이는 값이다.

`expiresAt` 을 3시간으로 잡은 근거는 새로 정한 게 아니다. `segment.py` 의 `GAP_HARD`
가 이미 "3시간 이상 벌어지면 다른 대화"로 쓰고 있다. 같은 기준을 쓰면 만료된 상태 문구가
새 세그먼트로 넘어가지 않는다. **워커가 "안 나눈다"고 판단하는 구간과 프론트가 "아직
유효하다"고 보는 구간이 어긋나면 안 된다.**

## 8. 파이프라인 배치와 비용

```
split()          분절                    LLM 1회  ← 반드시 먼저
   ↓
router.run()  ┬─ read_state()   실 상태    LLM 1회  ← 추가
              ├─ 말투 판정 → 말투 생성
              └─ harvest_memories() → 데이트 계획 → 카카오 → 데이트 문구
                                       └─ 유튜브 (말투 결과를 본 뒤)
```

**분절 다음에 놓는다.** 활성 맥락이 정해져야 무엇을 읽을지 정해진다.
**기억 추출·말투 판정과 나란히 놓는다.** 서로 결과를 쓰지 않으므로 순서가 없다.

### 비용

매 요청 고정 LLM 호출이 2회 → **3회**가 된다. `docs/contract-review.md` 에서 타임아웃
30초를 제안하며 정리한 표에 한 줄이 추가되는 셈이다.

**상태 산출은 기억 추출·말투 판정과 동시에 돈다** (`router.run()`). 셋이 서로 결과를 쓰지
않아서 호출이 하나 늘어도 벽시계는 거의 그대로다 — 실측에서 요청당 **16~32% 단축**됐다.

**분절 호출에 합치지 않는다.** 분절 출력에 필드를 하나 더 얹으면 출력 토큰이 늘고,
그게 그대로 지연이 된다 — 근거 문구(`note`) 한 줄을 뺐더니 4.0초가 2.3초가 됐다
(`docs/segmentation-v3.md` 9장). 같은 실수를 반대 방향으로 하지 않는다.

**폴백이 워커를 죽이지 않는다.** 상태 산출 실패는 오류가 아니라 "이번엔 갱신 없음"이다.
`segment.py` 의 `_score()` 가 실패를 `None` → 안 나눔으로 처리하는 것과 같은 방식이다.

## 9. 서버에 알릴 것 — **규격 변경 없음.** 동작 확인 2건 + 통보 1건 + 제안 1건

> 📄 **전달 문서는 `docs/server-handoff-v5.md` 다.** 서버 담당자가 그것만 읽으면 되도록
> 자체 완결로 썼다. 이 장은 **왜 그렇게 정했는지**를 남기는 자리다.

**`emotionAnalyses` 로 충분하다.** 새 `resultType` 도, 새 배열도, **필수 필드 추가도 없다.**
규격서 11장이 이 기능의 자리를 이미 비워 뒀고, `docs/contract-review.md` 에서 "명세가
나오면 채우겠다"고 답해 둔 그 자리다. **협의는 사실상 끝나 있다.**

| | 항목 | 성격 |
| --- | --- | --- |
| 🔴 1 | `SKIPPED` 가 사실상 사라진다 | **동작 변경.** 전송을 건너뛰면 ①번 줄이 영영 안 뜬다 |
| 🔴 2 | `emotionAnalyses` 도 `viewerParticipant` 로 갈라서 전송 | **동작.** 안 가르면 A 화면에 B 것이 뜬다 |
| 🟢 3 | `emotionType` 5종 · `intensityValue` 0~5 · `expiresAt` 3시간 | **통보.** 규격서가 "추후 확정"으로 비워둔 칸을 채우는 것 |
| 🔵 4 | `emotionAnalyses[].stateText` (String, **선택**) | **제안.** 안 받아도 그만이다 |

**🔴 두 개가 전부 필드가 아니라 동작이다.** 규격서 대조만으로는 드러나지 않는다 —
스키마는 그대로인데 서버가 그걸 어떻게 다루느냐가 바뀐다. 그래서 전달 문서 앞머리에 뒀다.

2번은 `results` 의 `INDIVIDUAL` 을 `targetParticipant` 로 가르는 것과 같은 규칙인데
**가르는 키가 다르다** (`visibilityType`/`targetParticipant` → `viewerParticipant`).
방 단위로 브로드캐스트하면 A 가 자기 자신의 상태를 보게 되고, "상대방 감정 showing"이라는
기능의 의미가 통째로 뒤집힌다.

### 🟢 3 — 값 정의 통보

7장 표대로 보낸다. 한 가지만 설명이 필요하다 — **필드 이름은 `emotionType` 인데 값은
상태 라벨**(`STABLE` · `RESOLVED` · `ACCUMULATED` · `ENGAGED` · `ESCALATED`)이다.
디자인 확정안의 축이 이쪽이고 실 모양과 1:1 이라 그렇다 (7장). 서버는 이 값을 저장만
하면 되고 해석할 일이 없다.

`category` enum 때와 같은 사고를 막으려는 통보다 — 워커가 보내는 값이 규격에 없어
응답 검증에서 반려되는 상황.

### 🔵 4 — 문구 필드는 이제 "있으면 좋은 것"으로 내렸다

초안에서는 이걸 🔴 필수로 잡았었다. **디자인 확정안이 나오면서 근거가 약해졌다.**

확정 표는 `상태 라벨 → 실 모양 · 글로우 · 문구`가 **한 표에 묶여 있고, 프론트는 이 표를
어차피 구현해야 한다** (실 모양과 글로우 때문에). 문구 열만 워커가 따로 실어 보내면
같은 표가 두 군데로 쪼개진다.

| | 워커가 보낸다 (`stateText`) | 프론트가 표를 갖는다 |
| --- | --- | --- |
| 서버 작업 | String 컬럼 1개 | **없음** |
| 절대 제약 | 하드 필터가 검사한다 | 문구가 **고정 5개**라 1회 리뷰로 끝난다 |
| 표의 일관성 | 문구만 다른 곳에서 온다 | **한 표에 모여 있다** |
| 나중에 | 라벨당 문구 변형·상황별 조정이 가능 | 라벨 1개 = 문구 1개로 고정 |

**절대 제약 논거가 여기서는 약하다.** 하드 필터가 지키려는 것은 매 요청 새로 생기는
문자열(LLM 생성물, 유튜브 제목)이다. 문구가 **상수 5개**면 화면에 나가기 전에 사람이
한 번 읽으면 끝난다 — `copy.py` 의 `TONE_GUIDE` 와 같은 성격이다.

그래서 **선택 필드로 제안하고, 안 받아주면 그냥 생략한다.** 규격서 14장의 "선택 필드에
값이 없으면 필드 생략"을 그대로 따르면 되고 `videoSummary` 와 같은 처지가 된다.
**어느 쪽이든 워커 로직은 같다** — 사전은 `copy.py` 에 두고 devui·트레이스에서 쓴다.

> ### 워커 노트 — 요청 4건에서 0건까지 내려온 경위
>
> | | 왜 뺐나 |
> | --- | --- |
> | `trend` 필드 | 확정안의 `RESOLVED`·`ACCUMULATED`·`ESCALATED` 가 추이를 **라벨 안에 이미 담고 있다.** 별도 축이 필요 없다 |
> | 요청 `previousEmotions` | 있으면 요청 경계를 넘는 추이가 정확해지지만, 없어도 스트림 안에서 판단된다(4장②). **정확도 문제지 구현 가능 여부가 아니다** |
> | `stateText` 필수 → 선택 | 위 |
>
> `recentResults` · `speakerProfiles` 는 **없으면 규칙 자체가 구현 불가**라 🔴 였다.
> 이번 것들은 성격이 다르다. **서버에 던지는 요청이 많아질수록 정말 필요한 그 두 개가 묻힌다.**

### 🔴 1 — `status` 가 사실상 항상 `COMPLETED` 가 된다

규격서 12장은 `COMPLETED` 를 "기능 결과 **또는 감정 분석 결과**가 존재"로 정의한다.
이 기능이 상시 작동하면 `emotionAnalyses` 가 매번 차므로 **`SKIPPED` 는 거의 나오지
않는다** — 상태 산출까지 실패했을 때만 남는다.

지금 `worker/pipeline.py` 는 `results` 가 비면 `SKIPPED` 를 돌려준다. 이 로직이 바뀐다.
**서버가 `SKIPPED` 를 "아무것도 안 함"으로 보고 전송을 건너뛰고 있다면 한 줄 문구가
영영 안 뜬다.** 반드시 알려야 한다.

## 12. 검증 — 실측 (2026-08-17)

**문구가 아니라 라벨이 맞는지를 먼저 본다.**

| 픽스처 | 기대 | 실측 |

| `case8_banter` | 장난이므로 `ENGAGED`. **`ESCALATED` 면 실패** | ✅ 양쪽 활기4 → `ENGAGED`, 분노 0. ②줄은 빈 줄 |

| `case4_routine` | 사흘치 룰 컷. 마지막 날만 | ✅ 네 축 전부 0, 확신 없음 → 양쪽 `STABLE` |

`shouldShow: false` 는 **그 사람 발화가 활성 맥락에 아예 없을 때만** 나온다.
`case3_one_sided` 의 B 는 "ㅇㅇ" · "응" 같은 리액션이라도 발화가 있어서 `true` 다 —
이 픽스처로는 그 경로가 안 걸린다.

### 두 번 고쳤다 — 실측이 아니었으면 못 봤을 것들

전 픽스처의 라벨 분포와 반복 실행 흔들림을 재서 잡았다.

**① 라벨이 화자를 건너뛰었다.** `case7_tone` 의 B(사과하는 쪽)에게 `ESCALATED` 가 붙었고,
모델이 쓴 `note` 는 "격앙되지는 않았으나"였다 — **근거와 라벨이 서로 어긋나 있었다.**
대화 전체의 온도를 두 사람에게 똑같이 칠한 것이다.
→ `state.md` 에 "그 화자가 **직접 쓴 말만** 보고 채점한다" + "`note` 는 반드시 점수의
근거여야 한다"를 넣어 잡았다.

**② 말투 교정과 상태 산출이 한 발화를 다르게 읽었다.** `case11_mixed` 의 "너 맨날 이런
식이지"를 말투 게이트는 공격 표현으로 잡는데 상태는 `ACCUMULATED`(서운함) 3회 고정이었다.
같은 유형인 `case7` 의 "야 너는 맨날 그런 식이야"는 `ESCALATED` 였다 — **같은 화법이
케이스마다 다른 라벨을 받았다.**
→ 라벨을 LLM 밖으로 빼고 `ANGER_WINS` 임계로 잡았다 (6장).

| | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| `case11` A | `ACCUMULATED` ×3 | **`ESCALATED` ×3** — 말투 교정과 일치 |
| `case7` A | `ESCALATED` ×3 | `ESCALATED` ×3 |
| `case7` B | `STABLE` ×2 / `RESOLVED` ×1 (흔들림) | **`RESOLVED` ×3** (고정) |
| `case9` | `RESOLVED` (애정3 = 활기3 동점) | **`ENGAGED`** — 데이트 계획에 "다정해 보여요"는 화해로 읽힌다 |

### 라벨 분포 (전 픽스처 11개 × 2명 = 22건)

```
STABLE 12   ENGAGED 5   ESCALATED 2   ACCUMULATED 2   RESOLVED 1
```

**5종이 전부 나온다.** `STABLE` 이 55%인데, 픽스처 절반(`case1` · `case2` · `case4` ·
`case5` · `case6`)이 감정 신호가 없는 일상 잡담이라 그게 맞는 값이다 —
"평온해요"가 뜨는 게 정상인 대화들이다.

### 반복 안정성 (같은 입력 3회)

6개 케이스 중 **5개 고정.** `case10_concern` 의 B 만 `RESOLVED` ×2 / `ACCUMULATED` ×1 로
흔들리는데, 사과하면서 동시에 답답해하는 발화라 둘 다 타당하다.

### 상시 검사

문구는 `copy.STATE_TEXT` 상수 5개고 **임포트 시점에** 10자 · 어미 · `filter.BANNED`
미포함을 검사한다. 화면에 나간 뒤에 발견하지 않는다.

## 13. 프론트 연동 — 민상님께

워커가 내보내는 값과 화면 규칙만 정리했다. **`devui` 에 같은 구조를 구현해 뒀으니
동작을 보고 싶으면 그쪽을 켜면 된다** (`.venv/bin/python devui/server.py`).

### ①번 줄 — `emotionAnalyses` 에서 **내 것 하나**를 고른다

```js
const mine = res.emotionAnalyses.find(s => s.viewerParticipant === myKey);
```

배열에 2건이 들어 있다. `viewerParticipant` 가 **보는 사람**이고
`subjectParticipant` 가 **감정의 주인**이다. 둘이 다르다 — **각자 상대방의 상태를 본다.**
A 화면과 B 화면의 ①번 줄 내용이 서로 다른 게 정상이다.

> **필드가 8개지만 최소 2개만 읽으면 화면이 그려집니다** — `viewerParticipant`(내 것 고르기)
> + `emotionType`(실 모양·글로우·문구). 나머지는 필요해질 때 쓰면 되고, **안 읽어도
> 아무 문제 없습니다.** 8개인 이유는 규격서 11장이 원래 그 모양이라서지, 프론트가
> 다 다뤄야 해서가 아닙니다.
>
> 서버가 수신자별로 갈라 보내면 배열에 내 것 1건만 올 수도 있다. 그때도 위 코드는 그대로
> 동작한다.

| 필드 | 쓰는 법 |
| --- | --- |
| `stateText` | **화면에 그대로 출력한다.** 10자 이하 보장 |
| `emotionType` | 실 모양·글로우를 고르는 키. 아래 5종 |
| `intensityValue` | `0.0`~`5.0`. 글로우 세기·진폭 같은 **강약**에만 쓴다 |
| `shouldShow` | `false` 면 **직전 문구를 그대로 둔다.** 화면을 비우는 게 아니다 |
| `expiresAt` | 이 시각이 지나면 문구를 내린다 (마지막 메시지 +3시간) |
| `subjectParticipant` | 누구의 상태인지. 화면에 표시할 필요는 없다 |

| `emotionType` | 실 모양 | 글로우 | `stateText` |
| --- | --- | --- | --- |
| `STABLE` | 아래로 축 늘어진 곡선 | 없음 (무채색) | 평온해요 |
| `RESOLVED` | 중앙에 하트 매듭 | 핑크·마젠타 | 다정해 보여요 |
| `ACCUMULATED` | 중앙이 엉킨 매듭 | 파랑 | 서운해 보여요 |
| `ENGAGED` | 크고 규칙적인 파동 | 초록 | 신나 보여요 |
| `ESCALATED` | 날카롭고 좁은 스파이크 | 빨강 | 감정이 올라와요 |

`stateText` 는 **규격서에 없는 선택 필드**다. 서버가 저장·전달하지 않기로 하면 빠져서
올 수 있으니, **위 표를 프론트에도 넣어 두고 없으면 `emotionType` 으로 매핑**하면 된다.
라벨당 문구는 1개로 고정이라 매핑에 분기가 없다.

> ⚠️ **실 옆에 상태 이름을 글자로 붙이지 말아 주세요.** "팽팽함", "감정 쌓임", `ACCUMULATED`
> 같은 라벨이 화면에 글자로 뜨면 이 프로젝트의 절대 제약(`CLAUDE.md`)이 깨집니다.
> 그림은 괜찮고 글자가 안 됩니다 — 화면에 나가는 글자는 `stateText` 한 줄뿐입니다.
> 강도(`4.0`)도 숫자로 노출하지 않습니다.

### ②번 줄 — `results`

- **우선순위 순으로 정렬해서 보낸다.** 한 줄만 쓰면 `results[0]` 을 쓰면 된다
- 미발동이면 빈 배열이다. **빈 줄이 정상 상태다** — 오류가 아니다
- `visibilityType` 이 `INDIVIDUAL` 이면 `targetParticipant` 인 사람에게만 보여야 한다.
  **상대는 그런 게 떴다는 사실 자체를 몰라야 한다** (설계상 의도된 것)

### 두 줄은 서로 밀어내지 않는다

3종이 전부 미발동이어도 ①번 줄은 남고, 데이트 카드가 떠도 ①번 줄이 밀려나지 않는다.
**②의 빈 줄은 정상이고, ①의 빈 줄은 사고다** — ①이 비면 워커 쪽 문제이니 알려 주세요.

### 확인 부탁드리는 것 2가지

1. **②번 줄이 한 줄이면 3종 동시 발동 시 하나만 뜬다.** 그러면 워커의 정렬 순서가 곧
   화면 선택이 된다. 이 해석이 맞는지 (11장 미결 3)
2. **`shouldShow: false` 일 때 직전 문구를 유지하는 동작**이 가능한지 (11장 미결 4)
