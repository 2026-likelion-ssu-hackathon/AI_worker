아래 "가능" 항목은 전부 실제로 동작하는 상태다.** 픽스처를 규격서 요청 형식 그대로 넣어

## 🔴 1. 요청에 `recentResults` (최근 추천 이력)

규격서 10장에 이 규칙이 있습니다.

> 동일 영상을 최근에 추천한 경우 다른 후보 탐색

**워커는 이걸 지킬 수단이 없습니다.** REST 동기 요청은 매번 상태가 없고, 요청 페이로드에
과거 추천 이력이 들어오지 않습니다. 워커가 자체 DB 를 갖는 건 "AI 결과 저장은 백엔드"
라는 2장 역할 구분과 어긋납니다.

데이트 코스도 같은 문제입니다. 같은 커플에게 매번 같은 코스를 추천하게 됩니다.

```json
"recentResults": [
  { "resultType": "YOUTUBE_RECOMMENDATION", "referenceKey": "abc123",  "createdAt": "2026-08-14T21:00:00" },
  { "resultType": "DATE_RECOMMENDATION",    "referenceKey": "성수다락", "createdAt": "2026-08-10T19:00:00" }
]
```

`referenceKey` 는 유튜브면 `videoId`, 데이트면 `mainPlace.name` 정도면 충분합니다.
최근 30일 / 최대 20건이면 됩니다. **이게 없으면 해당 규칙은 구현 불가로 남습니다.**

## 🔴 2. 요청에 `speakerProfiles` (화자별 말투 기준선)

말투 교정의 핵심은 **"그 사람의 평소 대비 변화량"** 입니다. 절대 기준으로 판정하면
평소 "ㅇㅇ"를 쓰는 커플에게 상시 오발동합니다.

그런데 3장 흐름이 "설정된 메시지 개수 누적 → 분석 요청" 이라, 요청에 최근 N개(20개 가정)만
들어오면 **그 20개로 평소 말투를 계산하게 됩니다.** 방금 화나서 보낸 메시지까지 "평소"에
포함되므로 변화량이 잡히지 않습니다.

방법이 두 가지입니다.

**(a) 요청에 과거 대화를 더 넣는다** — 화자당 최근 100개 이상. 페이로드가 커집니다.

**(b) 백엔드가 화자별 말투 프로필을 저장하고 요청에 실어준다** ← **이쪽을 제안합니다**

```json
"speakerProfiles": [
  {
    "participantKey": "USER_A",
    "avgLength": 21.0,       // 평균 메시지 길이
    "periodRate": 0.03,      // 마침표로 끝내는 비율
    "laughPerMsg": 2.8,      // 메시지당 ㅋ/ㅎ 개수
    "emojiRate": 0.35,       // 이모지 포함 비율
    "topAddress": ["오빠", "자기"]   // 평소 호칭 상위 2개
  }
]
```

다섯 값 모두 저장된 메시지에서 기계적으로 집계되는 값이라 LLM 이 필요 없습니다
(워커의 `worker/profile.py` 가 같은 계산을 하고 있으니 산식이 필요하면 드리겠습니다).
갱신 주기는 하루 1회면 충분합니다.

지금은 `data/speaker_profiles.json` 시드로 동작하고 있어 시연에는 문제가 없지만,
실제 서비스에서는 커플마다 값이 달라야 합니다. **이 필드가 없으면 워커는 요청에 들어온
메시지로 기준선을 계산하는 폴백으로 떨어지고, 위 이유로 판정이 무력화됩니다.**

## 🔴 3. `category` enum 확정

장소 `category` 는 규격서 예시에 `RESTAURANT` / `SHOP` 두 개만 등장하고 값 목록이 없습니다.
워커는 카카오 `category_group_code` 를 매핑해 **아래 8개 중 하나**를 보내고 있습니다.

```
RESTAURANT  CAFE  CULTURE  ATTRACTION  LODGING  SHOP  ACTIVITY  ETC
```

백엔드가 응답을 enum 으로 검증한다면 `CAFE` · `ATTRACTION` 같은 값이 반려됩니다.
데이트 코스는 카페·공원이 거의 반드시 들어가는 기능이라 실제로 걸립니다.
**위 8개로 확정해 주시거나, 줄여야 할 값이 있으면 알려주세요** — 워커 쪽 매핑을 맞추겠습니다.

## 🟢 4. 1회 요청 메시지 개수 + 타임아웃

**분석에 필요한 메시지 범위: 최근 20~30개면 충분합니다.** (말투 기준선은 위 2번 별도)

- 말투 교정 — 마지막 메시지 1개 + 직전 3턴 (반어·장난 판별용)
- 데이트 코스 — 최근 12개에서 데이트 의도 탐색
- 유튜브 — 최근 12개에서 고민 신호 탐색
- 기억 추출 — 최대 60개까지 받으면 좋지만 없어도 동작합니다

**타임아웃은 30초를 제안합니다.** 근거:

| 기능 | LLM 호출 | 외부 API |
| --- | --- | --- |
| 기억 추출 (매 요청) | 1회 | — |
| 말투 교정 | 2회 (판정 → 생성) | — |
| 데이트 코스 | 2회 (계획 → 문구) | 카카오 2~4회 |
| 유튜브 | 2회 (분류 → 선정) | 유튜브 3~7회 |

지금은 순차 실행이라 최악의 경우가 깁니다. 후보 기능을 병렬로 돌려 단축할 수 있는데,
**타임아웃 기준을 먼저 주시면 거기 맞춰 최적화하겠습니다.** 15초로 잡으셔야 한다면
병렬화 + 후보 축소가 필요합니다.

## 검토했지만 서버 작업이 필요 없는 것

초안을 보고 제안했다가 코드를 대조해 보니 서버가 손댈 필요가 없다고 판단한 항목입니다.
기록만 남깁니다.

| 항목 | 결론 |
| --- | --- |
| `requestedAt`(현재 시각) 추가 | **불필요.** 워커가 LLM 에 넘기는 대화 로그에 메시지별 `HH:MM` 이 이미 들어가 시간대 판단이 됩니다. 워커 DTO 에 선택 필드로만 두고(픽스처 재현용), 없으면 마지막 메시지 시각을 씁니다 |
| `videoSummary` 필드 제거 | **규격서 그대로 둡니다.** 명세 수정으로 화면에서 빠졌지만, 워커는 유튜브가 준 설명이 있으면 채우고 없으면 14장대로 필드를 생략합니다. 프론트가 안 쓸 뿐 규격을 고칠 이유는 없습니다 |
| 오류 코드 정리 | **그대로 씁니다.** `YOUTUBE_SEARCH_FAILED` 는 워커가 반환하지 않고(검색 실패는 `SKIPPED`), `ANALYSIS_TIMEOUT` 은 백엔드가 스스로 기록하는 값입니다. 남아 있어도 무해합니다 |
| `guideMessage` 를 프론트 상수로 이관 | **규격서대로 워커가 보냅니다.** `worker/copy.py` 상수 3개로 관리 중입니다 |
| `emotionType` / `intensityValue` 정의 | **PM 명세 대기.** 11장 명세가 나온 뒤 협의합니다. 그때까지 워커는 `emotionAnalyses: []` |
| 위젯 슬롯 1개인지 | **프론트(민상) 결정 사항.** 워커는 규격대로 전부 실어 보내고 우선순위 순으로 정렬합니다. 하나만 쓰시면 `results[0]` |

참고로 워커 쪽에서 규칙을 하나 넣어뒀습니다 — **말투 교정이 발동한 요청에서는 유튜브
추천을 보류합니다.** 방금 공격적인 메시지를 보낸 사람에게 교정 제안과 영상 카드가 동시에
뜨면 훈계처럼 읽혀서입니다. 정책이 정해지면 조정하겠습니다.

## 워커가 이미 맞춰둔 것 (참고)

- 요청·응답 DTO 전부 (`worker/models.py`) — camelCase 직렬화, 선택 필드 생략, 빈 목록 `[]`
- `USER_A`/`USER_B` ↔ 내부 `A`/`B` 변환
- `sentAt` 에 타임존이 없으면 KST 로 해석 (규격서 예시가 오프셋 없이 옵니다)
- `COMPLETED` / `SKIPPED` / `FAILED` 분기, `INVALID_REQUEST` · `INVALID_PARTICIPANT` · `MODEL_ERROR`
- 픽스처를 규격서 요청 형식 그대로 교체 (`fixtures/*.json`)

**아직 안 만든 것: HTTP 서버.** 규격서가 초안 v1 이고 미확정 항목이 남아 있어서,
지금은 판정 로직과 DTO 만 맞춰두고 CLI 로 검증하고 있습니다.
위 항목들이 확정되면 `analyze()` 함수를 핸들러에 그대로 물리면 됩니다 — 반나절이면 붙습니다.
