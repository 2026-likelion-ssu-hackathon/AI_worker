## 🔴 1. 중복 방지에 필요한 상태가 요청에 없다

규격서 10장에 이 규칙이 있다.

> 동일 영상을 최근에 추천한 경우 다른 후보 탐색

**워커는 이걸 지킬 수단이 없다.** REST 동기 요청은 매번 상태가 없고, 요청 페이로드에 과거
추천 이력이 들어오지 않는다. 워커가 자체 DB 를 갖는 건 "AI 결과 저장은 백엔드" 라는 2장
역할 구분과 어긋난다.

데이트 코스도 같은 문제다. 같은 커플에게 매번 같은 코스를 추천하게 된다.

**요청에 최근 결과 이력을 넣어주시면 좋겠습니다.**

```json
"recentResults": [
  { "resultType": "YOUTUBE_RECOMMENDATION", "referenceKey": "abc123",  "createdAt": "2026-08-14T21:00:00" },
  { "resultType": "DATE_RECOMMENDATION",    "referenceKey": "성수다락", "createdAt": "2026-08-10T19:00:00" }
]
```

`referenceKey` 는 유튜브면 `videoId`, 데이트면 `mainPlace.name` 정도면 충분합니다.
최근 30일 / 최대 20건이면 됩니다. 이게 없으면 해당 규칙은 **구현 불가**로 남습니다.

## 🔴 2. 말투 기준선에 필요한 과거 대화가 요청에 없다

말투 교정의 핵심은 **"그 사람의 평소 대비 변화량"** 입니다. 절대 기준으로 판정하면
평소 "ㅇㅇ"를 쓰는 커플에게 상시 오발동합니다.

그런데 3장 흐름이 "설정된 메시지 개수 누적 → 분석 요청" 이라, 요청에 최근 N개(20개 가정)만
들어오면 **그 20개로 평소 말투를 계산하게 됩니다.** 방금 화나서 보낸 메시지까지 "평소"에
포함되므로 변화량이 잡히지 않습니다.

방법이 두 가지입니다.

**(a) 요청에 과거 대화를 더 넣는다** — 화자당 최근 100개 이상. 페이로드가 커집니다.

**(b) 백엔드가 화자별 말투 프로필을 저장하고 요청에 실어준다** ← **이쪽을 제안합니다**

```json
"speakerProfiles": [
  {
    "participantKey": "USER_A",
    "avgLength": 21.0,       // 평균 메시지 길이
    "periodRate": 0.03,      // 마침표로 끝내는 비율
    "laughPerMsg": 2.8,      // 메시지당 ㅋ/ㅎ 개수
    "emojiRate": 0.35,       // 이모지 포함 비율
    "topAddress": ["오빠", "자기"]   // 평소 호칭 상위 2개
  }
]
```

페이로드가 커지지 않고, 워커가 응답에 갱신된 프로필을 실어 보내면 백엔드가 덮어쓰는
구조로 만들 수 있습니다. **응답에 `updatedSpeakerProfiles` 배열을 추가해도 될까요?**

지금은 `data/speaker_profiles.json` 시드로 동작하고 있어 시연에는 문제가 없지만,
실제 서비스에서는 커플마다 값이 달라야 합니다.

## 🟡 3. `requestedAt` 추가 요청

요청에 **현재 시각**이 없습니다. 데이트 코스 추천이 시간대를 봐야 하는데
(밤 10시 대화에 브런치를 추천하면 안 됨), 워커는 "지금 몇 시인지"를 알 수 없습니다.

수신 시각으로 대체할 수는 있지만, 그러면 같은 요청을 재현할 수 없어 테스트가 불안정해집니다.
`requestedAt` 한 필드만 추가 부탁드립니다. 지금은 없으면 마지막 메시지 시각으로 대체합니다.

## 🟡 4. `videoSummary` 필드를 빼는 것을 제안드립니다

**2026-08-16 유튜브 기능 명세 수정으로 이 필드를 쓸 화면이 없어졌습니다.**
화면에서 `[영상 요약 정보]` 가 삭제되고, **근거 문구(`recommendationReason`)가 그 역할을
흡수**했습니다. 근거 문구가 `현재 상황 + 영상과의 연결점 + 보고 나면 알게 되는 것`
세 요소를 담는 구조로 바뀌었습니다.

```
[카카포 안내 문구]
[영상 썸네일] [영상 제목] [채널명]
[왜 이 영상을 추천하는지 근거 문구]   ← 요약 자리를 대체
```

원래 이 필드에는 규격서 규칙("AI 생성 금지, PM 데이터셋 값만 반환")과 기능 명세(실시간
유튜브 검색)가 양립하지 않는 문제도 있었습니다. 실시간 검색으로 찾은 영상은 PM 데이터셋에
없기 때문입니다. **명세 수정으로 이 충돌 자체가 사라졌습니다.**

빼기 어려우시면 그대로 두셔도 동작에는 문제가 없습니다 — 워커는 유튜브가 주는 영상 설명이
있으면 채우고, 없으면 규격서 14장대로 필드를 생략합니다(실측상 설명이 빈 영상이 흔합니다).
어느 쪽이든 **프론트는 이 필드를 쓰지 않습니다.**

## 🟡 5. 위젯 슬롯 정책 확인 (프론트)

규격서 6장은 "여러 기능 동시 발동"을 허용하고 `results` 가 배열입니다. 반면 기존 설계는
**위젯 슬롯 1개**(공통/개별 중 하나만, 새 코멘트가 이전 것을 교체)였습니다.

워커는 규격대로 **전부 실어 보내고 우선순위 순으로 정렬**해 둡니다.
하나만 쓰실 거면 `results[0]` 을 쓰시면 됩니다. 프론트 배치가 정해지면 알려주세요.

참고로 워커 쪽에서 한 가지 규칙을 넣어뒀습니다 — **말투 교정이 발동한 요청에서는 유튜브
추천을 보류합니다.** 방금 공격적인 메시지를 보낸 사람에게 교정 제안과 영상 카드가 동시에
뜨면 훈계처럼 읽혀서입니다. 정책이 정해지면 조정하겠습니다.

## 🟡 6. enum 정의가 없는 필드들

strict schema 로 반환해야 해서 값 목록이 필요합니다.

**`category` (장소)** — 예시에 `RESTAURANT` / `SHOP` 만 있습니다. 지금 워커는 카카오
`category_group_code` 를 아래로 매핑해 보내고 있습니다. 이대로 확정해도 될까요?

```
RESTAURANT  CAFE  CULTURE  ATTRACTION  LODGING  SHOP  ACTIVITY  ETC
```

**`emotionType` / `intensityValue`** — 11장에 "추후 확정"으로 되어 있습니다.
감정 분석 기능 명세가 아직 안 나와서 워커는 `emotionAnalyses: []` 로 보냅니다.
명세가 나오면 다시 협의하겠습니다.

## 🟡 7. `guideMessage` 는 워커가 보내는 게 맞을까요?

세 기능 모두 `guideMessage` 가 필수인데, 값이 대화 내용과 무관한 **고정 문구**입니다
("대신 이렇게 상대방에게 말해보세요."). AI 생성물이 아니라 디자인 카피에 가깝습니다.

워커가 보내면 문구 한 줄 바꿀 때마다 워커를 배포해야 합니다. **프론트 상수로 두는 게
낫지 않을까요?** 지금은 규격서대로 워커가 실어 보내고 있고 (`worker/copy.py`),
빼기로 하면 바로 뺄 수 있습니다.

## 🟢 8. 오류 코드 — 2건만 정리 제안

- **`YOUTUBE_SEARCH_FAILED` 는 실제로 안 쓰게 됩니다.** 13장 마지막 줄대로 검색 실패는
  기능 미발동(`SKIPPED`)이고, 그 외 유튜브 API 오류는 `EXTERNAL_API_ERROR` 로 충분합니다.
  남겨두셔도 워커는 반환하지 않습니다
- **`ANALYSIS_TIMEOUT` 은 백엔드 쪽 코드로 보입니다.** 타임아웃이 나면 워커는 응답 자체를
  못 보내므로, 백엔드가 스스로 기록하는 값이면 맞습니다

## 🟢 9. 메시지 범위와 타임아웃

**분석에 필요한 메시지 범위: 최근 20~30개면 충분합니다.** (말투 기준선은 위 ② 별도)

- 말투 교정 — 마지막 메시지 1개 + 직전 3턴 (반어·장난 판별용)
- 데이트 코스 — 최근 12개에서 데이트 의도 탐색
- 유튜브 — 최근 12개에서 고민 신호 탐색
- 기억 추출 — 최대 60개까지 받으면 좋지만 없어도 동작합니다

**타임아웃은 30초를 제안합니다.** 근거:

| 기능 | LLM 호출 | 외부 API |
| --- | --- | --- |
| 기억 추출 (매 요청) | 1회 | — |
| 말투 교정 | 2회 (판정 → 생성) | — |
| 데이트 코스 | 2회 (계획 → 문구) | 카카오 2~4회 |
| 유튜브 | 2회 (분류 → 선정) | 유튜브 3~7회 |

지금은 순차 실행이라 최악의 경우가 깁니다. 후보 기능을 병렬로 돌려 단축할 수 있는데,
**타임아웃 기준을 먼저 주시면 거기 맞춰 최적화하겠습니다.** 15초로 잡으셔야 한다면
병렬화 + 후보 축소가 필요합니다.

## 워커가 이미 맞춰둔 것 (참고)

- 요청·응답 DTO 전부 (`worker/models.py`) — camelCase 직렬화, 선택 필드 생략, 빈 목록 `[]`
- `USER_A`/`USER_B` ↔ 내부 `A`/`B` 변환
- `sentAt` 에 타임존이 없으면 KST 로 해석 (규격서 예시가 오프셋 없이 옵니다)
- `COMPLETED` / `SKIPPED` / `FAILED` 분기, `INVALID_REQUEST` · `INVALID_PARTICIPANT` · `MODEL_ERROR`
- 픽스처를 규격서 요청 형식 그대로 교체 (`fixtures/*.json`)

**아직 안 만든 것: HTTP 서버.** 규격서가 초안 v1 이고 미확정 항목이 남아 있어서,
지금은 판정 로직과 DTO 만 맞춰두고 CLI 로 검증하고 있습니다.
위 항목들이 확정되면 `analyze()` 함수를 핸들러에 그대로 물리면 됩니다 — 반나절이면 붙습니다.
