### 🔴 확인 부탁드립니다 — 저장이 조용히 실패할 수 있는 자리 2개

**① `emotionType` 을 어떤 값으로 검증하시나요?**

규격서 11장 **예시**에 `"ANGER"` 가 적혀 있는데, 그건 감정 종류가 미확정이던 시점의
자리표시자입니다. 워커가 실제로 보내는 값은 **디자인 확정 5종**입니다.

```
STABLE  RESOLVED  ACCUMULATED  ENGAGED  ESCALATED
```

예시를 보고 enum 을 만드셨다면 **모든 감정 분석 결과가 저장 단계에서 탈락합니다.**
정의는 `docs/server-handoff.md` 와 `docs/state-display-v4.md` 에 있습니다.

**② `intensityValue` 의 유효 범위를 어떻게 잡으셨나요?**

워커가 보내는 값은 **`0.0`, 또는 `3.0`~`5.0`** 입니다. 중간값(0.1~2.9)은 나오지 않습니다 —
네 축이 전부 임계(3) 아래면 "평온"으로 보고 강도를 `0.0` 으로 떨어뜨리기 때문입니다.

`1.0` 이상이나 `0` 초과로 검증하시면 **`STABLE` 이 전부 탈락합니다.** 그런데 `STABLE` 은
예외 케이스가 아니라 **가장 흔한 상태**입니다. 평온한 대화에서 ①번 줄이 통째로 안 뜨게 됩니다.

### 🟡 알고 계시면 되는 것 2개

**③ `stateText` 를 저장하시나요?** 규격서에 없는 선택 필드로, 화면에 그대로 뜨는 문구
(`"서운해 보여요"`)입니다. 저장하지 않으시면 프론트가 라벨 → 문구 매핑을 자체로 가져야
합니다. 어느 쪽이든 워커 로직은 같습니다.

**④ `speakerProfiles` 는 이번 범위에서 빠진 것으로 보입니다.** 안 보내셔도 워커는 시드
기준선으로 정상 동작하므로 **연동에는 문제가 없습니다.** 다만 그 시드는 특정 커플 한 쌍의
값이라, 실제로는 모든 커플이 같은 기준선으로 판정됩니다. 말투 교정이 "그 사람의 평소 대비"가
아니라 "시드 대비"가 되는 상태입니다. MVP 범위라면 그대로 두셔도 되고, 넣으실 때
산식이 필요하면 드리겠습니다 (아래 2번).

### 🔴 요청 빈도를 확인하고 싶습니다

규격서 3장은 "**설정된 메시지 개수 누적** → AI 워커에 공통 분석 요청"인데, PR 설명은
"메시지 저장 후 AI 워커 분석을 요청"으로 읽힙니다. **메시지 1건마다 1회 호출인가요,
N개 누적마다 1회인가요?**

메시지마다 호출이면 워커 쪽 비용이 이렇게 됩니다.

| | 메시지 1건당 | 30메시지 대화 |
| --- | --- | --- |
| OpenAI 호출 | 3~5회 | 90~150회 |
| YouTube 쿼터 (발동한 요청만) | 106 units | **하루 한도 10,000 의 상당 부분** |

OpenAI 는 감당 가능한 금액이지만, **YouTube 무료 쿼터는 하루 약 94회 발동이 상한**입니다.
소진되면 유튜브 추천이 **오류가 아니라 조용한 미발동**으로 바뀌어서, 화면에서는 "적절한
영상이 없었다"와 구분되지 않습니다. 시연 중이면 원인을 못 찾습니다.

누적 방식이면 **N 값만 알려주시면** 됩니다. 워커는 어느 쪽이든 동작합니다.

## 🔴 1. 요청에 `recentResults` (최근 추천 이력)

규격서 10장에 이 규칙이 있습니다.

> 동일 영상을 최근에 추천한 경우 다른 후보 탐색

**워커는 이걸 지킬 수단이 없습니다.** REST 동기 요청은 매번 상태가 없고, 요청 페이로드에
과거 추천 이력이 들어오지 않습니다. 워커가 자체 DB 를 갖는 건 "AI 결과 저장은 백엔드"
라는 2장 역할 구분과 어긋납니다.

데이트 코스도 같은 문제입니다. 같은 커플에게 매번 같은 코스를 추천하게 됩니다.

```json
"recentResults": [
  { "resultType": "YOUTUBE_RECOMMENDATION", "referenceKey": "abc123",  "createdAt": "2026-08-14T21:00:00" },
  { "resultType": "DATE_RECOMMENDATION",    "referenceKey": "성수다락", "createdAt": "2026-08-10T19:00:00" }
]
```

`referenceKey` 는 유튜브면 `videoId`, 데이트면 `mainPlace.name` 정도면 충분합니다.
최근 30일 / 최대 20건이면 됩니다.

> ✅ **합의됨 (2026-08-17). 워커가 받는 자리를 만들어 뒀습니다.**
> `AnalysisRequest.recentResults` 는 **선택 필드**라 안 보내셔도 지금처럼 동작하고,
> 보내주시면 유튜브는 같은 `videoId` 를 **LLM 에 보이기 전에** 후보에서 빼고,
> 데이트는 같은 상호명을 코스에서 뺍니다.

## 🔴 2. 요청에 `speakerProfiles` (화자별 말투 기준선)

말투 교정의 핵심은 **"그 사람의 평소 대비 변화량"** 입니다. 절대 기준으로 판정하면
평소 "ㅇㅇ"를 쓰는 커플에게 상시 오발동합니다.

그런데 3장 흐름이 "설정된 메시지 개수 누적 → 분석 요청" 이라, 요청에 최근 N개(20개 가정)만
들어오면 **그 20개로 평소 말투를 계산하게 됩니다.** 방금 화나서 보낸 메시지까지 "평소"에
포함되므로 변화량이 잡히지 않습니다.

방법이 두 가지입니다.

**(a) 요청에 과거 대화를 더 넣는다** — 화자당 최근 100개 이상. 페이로드가 커집니다.

**(b) 백엔드가 화자별 말투 프로필을 저장하고 요청에 실어준다** ← **이쪽을 제안합니다**

```json
"speakerProfiles": [
  {
    "participantKey": "USER_A",
    "avgLength": 21.0,       // 평균 메시지 길이
    "periodRate": 0.03,      // 마침표로 끝내는 비율
    "laughPerMsg": 2.8,      // 메시지당 ㅋ/ㅎ 개수
    "emojiRate": 0.35,       // 이모지 포함 비율
    "topAddress": ["오빠", "자기"]   // 평소 호칭 상위 2개
  }
]
```

다섯 값 모두 저장된 메시지에서 기계적으로 집계되는 값이라 LLM 이 필요 없습니다
(워커의 `worker/profile.py` 가 같은 계산을 하고 있으니 산식이 필요하면 드리겠습니다).
갱신 주기는 하루 1회면 충분합니다.

지금은 `data/speaker_profiles.json` 시드로 동작하고 있어 시연에는 문제가 없지만,
실제 서비스에서는 커플마다 값이 달라야 합니다.

> ✅ **합의됨 (2026-08-17) — 우선 목데이터로. 워커가 받는 자리를 만들어 뒀습니다.**
> 기준선은 **요청 값 > 시드 > 대화에서 계산** 순으로 씁니다 (`worker/profile.py`).
> 선택 필드라 안 보내셔도 지금처럼 시드로 돕니다.
>
> ⚠️ **목데이터는 배선을 여는 것이지 판정을 고치는 게 아닙니다.** 값이 실제 커플의
> 평소 말투가 아니면 "평소 대비 변화량"은 여전히 시드로 판정하는 것과 같습니다.
> 시연에는 충분하지만, 실서비스 전에 실제 집계로 바꿔야 이 기능이 제 값을 합니다.

## 🔴 3. `category` enum 확정

장소 `category` 는 규격서 예시에 `RESTAURANT` / `SHOP` 두 개만 등장하고 값 목록이 없습니다.
워커는 카카오 `category_group_code` 를 매핑해 **아래 8개 중 하나**를 보내고 있습니다.

```
RESTAURANT  CAFE  CULTURE  ATTRACTION  LODGING  SHOP  ACTIVITY  ETC
```

백엔드가 응답을 enum 으로 검증한다면 `CAFE` · `ATTRACTION` 같은 값이 반려됩니다.
데이트 코스는 카페·공원이 거의 반드시 들어가는 기능이라 실제로 걸립니다.
> ✅ **합의됨 (2026-08-17) — 위 8개 그대로 씁니다.** 워커 매핑 변경 없습니다.

## 🟢 4. 1회 요청 메시지 개수 + 타임아웃

**분석에 필요한 메시지 범위: 최근 20~30개면 충분합니다.** (말투 기준선은 위 2번 별도)

워커는 받은 메시지를 **화제 단위로 끊은 뒤 마지막 묶음만** 분석합니다
(`docs/segmentation-v3.md`). 그래서 넉넉히 주셔도 판정이 흐려지지 않습니다.

- 말투 교정 — 마지막 메시지 1개 + 직전 3턴 (반어·장난 판별용)
- 데이트 코스 / 유튜브 — 마지막 화제 묶음에서 의도·고민 신호 탐색
- 기억 추출 — 최대 60개까지 받으면 좋지만 없어도 동작합니다

## 검토했지만 서버 작업이 필요 없는 것

초안을 보고 제안했다가 코드를 대조해 보니 서버가 손댈 필요가 없다고 판단한 항목입니다.
기록만 남깁니다.

| 항목 | 결론 |
| --- | --- |
| `emotionType` / `intensityValue` 정의 대기 | **해소.** PM 명세가 나와서 위 5번으로 채웠습니다 |
| `requestedAt`(현재 시각) 추가 | **불필요.** 워커가 LLM 에 넘기는 대화 로그에 메시지별 `HH:MM` 이 이미 들어가 시간대 판단이 됩니다. 워커 DTO 에 선택 필드로만 두고(픽스처 재현용), 없으면 마지막 메시지 시각을 씁니다 |
| `videoSummary` 필드 제거 | **규격서 그대로 둡니다.** 명세 수정으로 화면에서 빠졌지만, 워커는 유튜브가 준 설명이 있으면 채우고 없으면 14장대로 필드를 생략합니다. 프론트가 안 쓸 뿐 규격을 고칠 이유는 없습니다 |
| 오류 코드 정리 | **그대로 씁니다.** `YOUTUBE_SEARCH_FAILED` 는 워커가 반환하지 않고(검색 실패는 `SKIPPED`), `ANALYSIS_TIMEOUT` 은 백엔드가 스스로 기록하는 값입니다. 남아 있어도 무해합니다 |
| `guideMessage` 를 프론트 상수로 이관 | **규격서대로 워커가 보냅니다.** `worker/copy.py` 상수 3개로 관리 중입니다 |
| 위젯 슬롯 1개인지 | **프론트(민상) 결정 사항.** 워커는 규격대로 전부 실어 보내고 우선순위 순으로 정렬합니다. 하나만 쓰시면 `results[0]` |

참고로 워커 쪽에서 규칙을 하나 넣어뒀습니다 — **말투 교정이 발동한 요청에서는 유튜브
추천을 보류합니다.** 방금 공격적인 메시지를 보낸 사람에게 교정 제안과 영상 카드가 동시에
뜨면 훈계처럼 읽혀서입니다. 정책이 정해지면 조정하겠습니다.
