## 1. 문제 — 픽스처가 가리고 있던 것

현재 픽스처는 **하나가 곧 하나의 대화**다. `case9_date.json` 은 처음부터 끝까지 주말 약속
얘기고, `case7_tone.json` 은 처음부터 끝까지 다툼이다. 실제 채팅방은 그렇지 않다.

규격서 3장의 흐름은 이렇다.

```
백엔드의 메시지 저장 → 설정된 메시지 개수 누적 → AI 워커에 공통 분석 요청
```

**서버는 최근 N개를 통째로 보낸다. 화제 경계를 모른다.** 그 N개 안에는 점심 메뉴 얘기,
두 시간 뒤의 다툼, 그 사이의 잡담이 전부 섞여 있다.

그런데 워커의 게이트는 전부 **고정 창(window)** 이었다.

| 단계 | 보던 범위 |
| --- | --- |
| 말투 교정 | 마지막 메시지 1개 (+ 직전 3턴 맥락) |
| 데이트 코스 | 최근 12개 (`WINDOW = 12`) |
| 유튜브 | 최근 12개 (`WINDOW = 12`) |
| 기억 추출 | 전체 |
| RAG 질의 | 리액션 뺀 최근 6발화 |

"최근 12개"는 **개수**지 **대화**가 아니다. 12개 안에 몇 개의 화제가 들어 있는지 아무도 모른다.

### 실측 — 실제로 깨졌다

주제가 한 번 바뀌는 스트림을 만들어 분절 전 파이프라인에 그대로 넣었다.

```
[20:02] A  이번 주 토요일에 뭐 하지? 우리 성수 갈까     ← 주말 약속
[20:04] B  좋지 카페 가고 싶다 ㅎㅎ
[20:06] A  배고파 마라탕도 땡기는데
[20:08] B  ㅋㅋ 그것도 좋고
[20:10] B  이따 얘기하자 나 지금 좀 바빠
        ⋯ 2시간 20분 침묵 ⋯
[22:30] A  연락 왜 안 봐                              ← 연락 문제로 다툼
[22:35] B  아 미안 이제 봤어
[22:37] A  너 맨날 이런 식이지.
```

결과 — **막 싸우기 시작한 사람들에게 데이트 코스가 나갔다.**

```
TONE_CORRECTION      INDIVIDUAL → USER_A   trigger=[208]        ← 맞다
DATE_RECOMMENDATION  COUPLE                trigger=[201, 202]   ← 나가면 안 된다
  코스   성수 마라탕과 카페 데이트 코스
```

고장이 네 겹이었다.

| # | 무엇이 | 왜 |
| --- | --- | --- |
| 1 | 다툼 중에 데이트 코스가 **양쪽 모두에게** 떴다 | 데이트 게이트가 12개 창에서 2시간 전 발화를 집었다 |
| 2 | **LLM 게이트도 못 막았다** (`should_recommend=true`) | 창 안에 있으면 LLM 에게도 "지금 대화"로 보인다 |
| 3 | `triggerMessageIds=[201, 202]` 가 2시간 반 전 메시지다 | 규격서 7장은 "결과를 **다시 노출할** 기준 메시지"다 |
| 4 | RAG 가 `커플 잠옷`, `둘이 챙겨 보는 예능` 을 물어왔다 | 질의가 두 화제를 이어 붙인 문자열이 됐다 |

②가 핵심이다. **"애매하면 LLM 이 걸러준다"가 이 구조의 마지막 방어선인데, 재료가 섞여
있으면 LLM 도 못 거른다.** 판정을 아무리 잘해도 잘못된 재료를 주면 소용이 없다.

### 이미 손으로 한 번 막아둔 적이 있다

`router.py` 의 `SUPPRESS_YOUTUBE_WHEN_TONE` 이 정확히 이 문제의 국소 처방이다. 같은 이유로
데이트 코스도 막았어야 하는데 안 막혀 있었다. 기능 쌍마다 상수를 하나씩 늘리는 건 답이
아니다 — 후보가 늘면 조합이 제곱으로 는다.

## 2. 세그먼트란 무엇인가

> **세그먼트** — 같은 화제로 이어지는 연속 메시지 묶음. **라우팅과 기억 추출의 단위.**

위 실측 스트림은 세그먼트 2개다.

```
┌─ 세그먼트 #1 ──────────────────────┐
│ 201~205  주말 약속 · light          │   ← 끝난 대화
└────────────────────────────────────┘
        ⋮  2시간 20분 침묵
┌─ 세그먼트 #2 (활성) ───────────────┐
│ 206~208  연락 문제로 다툼 · tense   │   ← 지금 벌어지는 대화
└────────────────────────────────────┘
```

메시지 개수가 아니라 **경계**가 기준이다.

## 3. 경계를 어떻게 찾는가

### 3-1. 재보고 버린 것들

경계 신호 후보를 네 가지 재봤다. **셋이 실측에서 무너졌다.**

| 방식 | 종류 | 결과 |
| --- | --- | --- |
| 화제 전환 표지어 | 단어 | ❌ **반대로 작동** |
| 어휘 겹침 | 숫자 | ❌ **변별력 0** |
| 임베딩 거리 | 숫자(의미) | ❌ **경계에서 오히려 낮음** |
| 시간 공백 | 숫자 | ✅ **유일하게 갈림** |

**표지어** — `case9_date` 는 단일 화제인데 세 번째 메시지가 `근데 만나서 뭐하지?` 로
시작한다. 반대로 위 실측 스트림의 진짜 경계(`206 연락 왜 안 봐`)에는 표지어가 없다.
**표지어가 있는 곳은 같은 화제였고, 화제가 바뀐 곳엔 표지어가 없었다.**
사람은 "그건 그렇고"라고 선언하고 화제를 바꾸지 않는다. 그냥 바꾼다.

**어휘 겹침** — 직전 3개와의 2글자 이상 토큰 교집합.

| | 겹치는 단어 수 |
| --- | --- |
| `case9` 같은 화제 안 인접 발화 | 0, 0, 0, 0, 1 |
| 실측 스트림의 진짜 경계 | 0 |

한국어라 조사가 붙어 `토요일에` 와 `토요일` 이 다른 토큰이고, 채팅 문장이 짧아 같은
화제여도 안 겹친다. **같은 화제에서도 0이면 신호가 아니다.**

더 결정적인 건 `case4_routine` 이다. 사흘치 대화인데 매일 같은 인사를 한다 —
`오늘 뭐했어?` / `그냥 회사 갔다 왔어` / `밥은 먹었어?`. **어휘는 거의 같은데 다른 대화
3개다.** 어휘 기준은 못 잡는 정도가 아니라 반대로 잡는다.

**임베딩 거리** — `retrieve.py` 가 이미 쓰는 `OpenAIEmbeddings` 로 인접 블록 코사인 거리.

```
실측 스트림 (진짜 경계는 206 하나)
  202  0.764   ← 같은 화제인데 최대
  205  0.684
  206  0.521   ← 진짜 경계인데 최소 축
```

`case9`(단일 화제)의 범위가 0.536~0.689, 경계가 있는 스트림이 0.506~0.764다.
**두 분포가 완전히 겹쳐 어떤 임계값을 그어도 갈리지 않는다.** 짧은 채팅에서 임베딩은
화제보다 **발화 형식**(질문·사과·리액션)을 더 강하게 반영한다.

**시간 공백** — 유일하게 살아남았다.

| | 값 |
| --- | --- |
| 단일 화제 안 최대 공백 (픽스처 10개 전체) | **9분** (`case7`) |
| 실측 스트림의 경계 | **140분** |
| `case4` 날짜 경계 | **1432분 / 1445분** |

### 3-2. 결론 — 룰은 시간 컷 하나, 나머지는 LLM

```
1. 시간 공백 3시간 이상  → 룰이 자른다 (LLM 에게 묻지 않는다)
2. 그 안쪽              → LLM 이 화제로 자른다
```

**채팅에서 화제 전환은 문자열이나 벡터 표면에 흔적을 거의 안 남긴다.**
`연락 왜 안 봐` 가 앞 대화와 다른 화제라는 건, 앞이 무슨 얘기였는지 알아야만 안다.
표면 특징으로 풀 수 있는 문제가 아니었다.

### 3-3. 3시간이라는 숫자의 근거

**실측으로 정한 값이 아니다.** 단일 화제 최대가 9분이고 경계가 140분 이상이라 그 사이가
텅 비어 있다. 목데이터라 "대화하다 1시간 끊기고 다시 이어지는" 패턴이 없다.

그래서 **틀렸을 때 복구 가능한 쪽으로** 정했다. 룰 컷은 *LLM 없이 확정*이라
**잘못 자르면 LLM 이 고칠 기회조차 없다.** 반대로 관대하게 잡으면 LLM 에게 넘어가고
거기서 고칠 수 있다. 그래서 넉넉한 3시간이다.

### 3-4. LLM 이 잘하는 것과 못하는 것 (실측)

프로토타입으로 4개 케이스 × 3회씩 돌렸다.

| 케이스 | 기대 | 결과 |
| --- | --- | --- |
| 실측 스트림 | 2개 | ✅ 2개 (3/3) |
| `case9_date` | 1개 | ✅ 1개 (3/3) |
| `case7_tone` | 1개 | ✅ 1개 (3/3) |
| `case4_routine` | 3개 | ❌ **1개 (3/3)** |

**`case7` 을 안 쪼갠 게 중요하다.** 이 대화는 `오빠 오늘 몇 시에 와?` 로 시작해
`야 너는 맨날 그런 식이야.` 로 끝난다 — 호칭이 바뀌고 이모지·ㅋ 가 사라지고 마침표로
끝난다. **말투는 극적으로 바뀌는데 화제는 하나다.** 프롬프트에 한 줄 넣는 것으로 3/3 지켜졌다.

**`case4` 실패가 오히려 설계를 확인해준다.** 공백 1432분짜리 사흘치를 하나로 봤다.
화제가 "일상 대화"로 같으니 LLM 입장에선 틀린 판단이 아니다. **LLM 은 화제는 보는데
시간은 못 본다.** 3시간 룰 컷이 정확히 이 구멍을 메운다.

> 숫자와 LLM 중 하나를 고르는 문제가 아니라 **서로 다른 구멍을 메우고 있다.**

### 3-5. 말투 변화는 경계가 아니다

말투·감정이 격해지는 건 **세그먼트의 속성(`mood`)이지 경계가 아니다.** 위 `case7` 이 근거다.

여기서 끊으면 `tone_judge` 가 직전 3턴을 잃는다. **왜 화가 났는지(야근으로 약속이 깨짐)를
못 보게 되고**, 대체 문장이 근거 없는 일반론이 된다. 지금 잘 되는 기능을 망가뜨린다.

## 4. 구현 — 어떻게 도는가

```
messages (전체)
   ↓
① 룰 컷      3시간 이상 공백에서 자른다              → 조각 N개
   ↓
② LLM 분절   마지막 조각만 화제로 나눈다 (1회 호출)   → 세그먼트
   ↓
segments[]   [ … 과거 … , 활성 ]
```

**LLM 은 마지막 조각에만 건다.** 라우팅도 기억 추출도 활성 세그먼트만 쓰기 때문에 앞
조각을 세밀하게 나눌 이유가 없다. 이 설계로 **LLM 호출은 요청당 정확히 1회**로 고정된다.

호출을 생략하는 경우:

- 마지막 조각이 3개 미만이다 (나눌 게 없다)
- 메시지가 하나도 없다

**LLM 은 `messageId` 목록만 돌려준다.** 본문을 다시 쓰게 하면 환각이 섞인다 —
장소·영상에 적용한 원칙과 같다. 받은 뒤 검증한다.

- 모든 메시지가 **정확히 한 번씩** 들어갔는가
- 순서가 유지되는가
- 요청에 없는 id 가 섞이지 않았는가

하나라도 어긋나면 **그 조각을 세그먼트 1개로** 처리한다 (폴백).

## 5. 어느 세그먼트를 분석하는가

> **라우팅은 활성 세그먼트(= 마지막 세그먼트)에만 건다.**

개입은 **지금 벌어지고 있는 대화**에 대해서 하는 것이다. 두 시간 전에 끝난 화제에 지금
카드를 띄우는 건 늦은 게 아니라 틀린 것이다.

1장의 고장은 **이 규칙 하나로 전부 고쳐진다.** 데이트 발화(201~205)는 활성 세그먼트가
아니므로 게이트가 아예 그 메시지를 보지 않는다. `triggerMessageIds` 도 자동으로 활성
세그먼트 안에 갇힌다.

| 상황 | 처리 |
| --- | --- |
| 활성 세그먼트가 짧다 (4개 미만) | 앞 세그먼트에서 뒤에서부터 채워 **맥락 4개**를 확보한다 |
| 과거 세그먼트 | 라우팅·기억 추출에 쓰지 않는다 |
| 세그먼트가 1개다 | 분절 전과 완전히 같다 |

**맥락과 트리거를 갈라 쓴다.** 이게 5장의 핵심이다.

| | 쓰는 것 | 이유 |
| --- | --- | --- |
| 게이트 판정 · 트리거 id · RAG 질의 · 기억 추출 | **활성 세그먼트만** | 과거 화제가 기능을 발동시키면 안 된다 |
| 말투 판정 프롬프트의 직전 대화 | **맥락(활성 + 부족분)** | 활성이 1개면 장난인지 갈등인지 구분할 수 없다 |
| 말투 기준선(`profile.py`) | **전체 스트림** | 기준선은 표본이 넓을수록 정확하다 |

**규격서 6장의 "여러 기능 동시 발동"을 어기지 않는다.** 활성 세그먼트 하나에서도 말투
교정과 유튜브가 같이 나올 수 있다. 제한하는 것은 *기능 개수*가 아니라 *화제*다.

## 6. 세그먼트 라벨은 내부용이다

`topic` · `mood` 는 라우팅·디버깅 재료이고 **화면에 절대 나가지 않는다.**

> ⚠️ LLM 이 `topic` 에 `"권태기 조짐"`, `"요즘 대화가 줄어든 것에 대한 다툼"` 같은 라벨을
> 붙일 수 있다. 이 프로젝트의 **절대 제약** 정면 위반이다.
>
> `filter.py` 는 **`AiResult` 의 화면 문자열만** 검사한다. 라벨은 검사 대상이 아니다.
> 그러므로 **라벨을 `resultData` 의 어떤 필드에도 싣지 않는 것**이 유일한 방어다.
> 추천 이유 프롬프트에도 넘기지 않는다. 넘기면 그대로 인용된다.

`mood` 는 규격서 11장의 **감정 분석(`emotionAnalyses`)과 다른 것**이다. 그쪽은 아직 명세가
없는 별도 기능이고 화면에 나간다. 이름이 비슷하니 섞지 않는다.

## 7. 기능별로 무엇이 달라지는가

| | 분절 전 | 분절 후 |
| --- | --- | --- |
| 말투 교정 | 마지막 메시지 1개 + 직전 3턴 | 그대로. 맥락이 **세그먼트를 넘지 않는다** |
| 데이트 코스 | 최근 12개 | 활성 세그먼트 전체 (`WINDOW` 삭제) |
| 유튜브 | 최근 12개 | 활성 세그먼트 전체 (`WINDOW` 삭제) |
| 기억 추출 | 전체 | 활성 세그먼트 |
| RAG 질의 | 최근 6발화 | 활성 세그먼트 안에서만 |
| `triggerMessageIds` | 창 안 아무 메시지 | 활성 세그먼트 안으로 제한 |
| `SUPPRESS_YOUTUBE_WHEN_TONE` | 필요 | **유지.** 화제가 같아도 개입 시점이 다르다는 별개 근거다 |

`WINDOW = 12` 두 개가 사라진다. **개수로 자르던 걸 화제로 자르는 게 이 변경의 본질이다.**

## 8. 비용과 레이턴시 (실측)

분절 호출은 이 파이프라인에서 **가장 싼 호출**이다. 판정만 하고 문장을 만들지 않는다.

| | 값 |
| --- | --- |
| 호출 시간 | **0.87 ~ 1.45초** (첫 호출 5.1초는 커넥션 수립) |
| 토큰 | 호출당 입력 약 424 / 출력 약 41 |
| 전체 대비 | 케이스당 6~12초 중 **+8~15%** |
| 타임아웃 30초 제안 (`contract-review` 4번) | 여유 있음 |

병렬화는 안 된다. 모든 후보가 분절 결과를 기다리므로 순차 체인에 그대로 더해진다.

### 그런데 순증이 아니다

1장의 실측 스트림 기준.

```
분절 전   extract + tone_judge + tone_suggest + plan_date + write_reason  = 5회 + 카카오 2회
분절 후   segment + extract + tone_judge + tone_suggest                   = 4회 + 카카오 0회
```

데이트 코스가 미발동하면 LLM 2회와 카카오 2회가 통째로 빠진다. **1회를 더하고 3회를 빼서
순감이다.** 잘못 발동하던 게 안 발동하니 그쪽 비용이 전부 사라진다.
순수하게 +1초인 것은 `case9` 같은 단일 화제 케이스뿐이다.
