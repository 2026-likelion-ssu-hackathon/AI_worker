## 1. 문제 — 픽스처가 가리고 있던 것

규격서 3장의 흐름은 이렇다.

```
백엔드의 메시지 저장 → 설정된 메시지 개수 누적 → AI 워커에 공통 분석 요청
```

**서버는 최근 N개를 통째로 보낸다. 화제 경계를 모른다.** 그런데 워커의 게이트는 전부
고정 창(최근 12개)이었다. "최근 12개"는 **개수**지 **대화**가 아니다.

### 실측 — 실제로 깨졌다

```
[20:02] A  이번 주 토요일에 뭐 하지? 우리 성수 갈까     ← 주말 약속
[20:04] B  좋지 카페 가고 싶다 ㅎㅎ
[20:06] A  배고파 마라탕도 땡기는데
[20:10] B  이따 얘기하자 나 지금 좀 바빠
        ⋯ 2시간 20분 침묵 ⋯
[22:30] A  연락 왜 안 봐                              ← 연락 문제로 다툼
[22:37] A  너 맨날 이런 식이지.
```

```
TONE_CORRECTION      INDIVIDUAL → USER_A   trigger=[208]        ← 맞다
DATE_RECOMMENDATION  COUPLE                trigger=[201, 202]   ← 나가면 안 된다
```

**막 싸우기 시작한 사람들에게 데이트 코스가 나갔다.** 그리고 **LLM 게이트도 못 막았다**
(`should_recommend=true`) — 창 안에 있으면 LLM 에게도 "지금 대화"로 보인다. 판정을 아무리
잘해도 재료가 섞이면 소용이 없다. `fixtures/case11_mixed.json` 이 이 케이스다.

## 2. 세그먼트란 무엇인가

> **세그먼트** — 같은 화제로 이어지는 연속 메시지 묶음. **라우팅과 기억 추출의 단위.**

라우팅은 **활성 세그먼트(= 마지막 세그먼트)에만** 건다. 개입은 지금 벌어지고 있는 대화에
대해서 하는 것이다. 두 시간 전에 끝난 화제에 지금 카드를 띄우는 건 늦은 게 아니라 틀린 것이다.

## 3. 판정 구조 — 점수는 LLM, 자르는 건 룰

### 3-1. 왜 바꾸는가

처음 구현은 **LLM 에게 대화를 통째로 주고 세그먼트 목록을 받는** 배치 방식이었다.
동작은 했지만 세 가지가 걸린다.

| | 배치 방식(전환 전) | 점수 방식(현재) |
| --- | --- | --- |
| 경계 결정 | LLM 안에서. **읽을 수도 고칠 수도 없다** | 코드의 임계값. 읽히고 튜닝된다 |
| 왜 잘렸나 | 알 수 없다 | 발화별 점수가 트레이스에 남는다 |
| 출력 검증 | id 분할이 정확한지 전량 대조. 어긋나면 통째로 폴백 | id 로 맞춰 붙인다. 하나 빠져도 그 발화만 넘어간다 |

**경계가 코드 밖에 있으면 조정할 손잡이가 없다.** 과분절이 나와도 프롬프트를 다시 쓰는 것
말고 할 수 있는 게 없고, 그건 재현 가능한 조정이 아니다.

### 3-2. 구조

```
messages
   ↓
① 룰 컷      3시간 이상 공백에서 자른다 (LLM 에게 묻지 않는다)
   ↓
② LLM 채점   마지막 조각의 발화마다 "직전 맥락과 얼마나 이어지는가"를 점수로 (호출 1회)
   ↓
③ 룰 판정    임계값으로 붙일지 자를지 결정한다
   ↓
segments[]   [ … 과거 … , 활성 ]
```

**LLM 은 경계를 정하지 않는다. 점수만 낸다.** 자르는 판단은 전부 ③에 있다.

### 3-3. LLM 이 내는 값

발화 하나하나에 대해 **직전까지의 맥락과 비교**해서 매긴다.

| 필드 | 범위 | 뜻 |
| --- | --- | --- |
| `same_context` | true/false | 이전 맥락과 같은 이야기인가 |
| `topic_score` | 0~100 | **화제가 이어지는 정도.** 100 에 가까울수록 같은 얘기 |
| `tone_score` | 0~100 | **말투가 이어지는 정도.** 100 에 가까울수록 평소 흐름 |

> ⚠️ **이름 주의.** "변화 점수"가 아니라 **연속성 점수**다. 높을수록 **안 바뀐 것**이다.
> 90~80점대면 "이전 맥락과 비슷하다"가 되도록 방향을 맞춰 놨다.

**점수 앵커를 프롬프트에 명시한다.** LLM 이 매기는 숫자는 그냥 두면 보정이 안 된다 —
85 와 75 의 차이가 호출마다 달라진다. 기준점을 글로 박아야 임계값이 의미를 갖는다.

```
100  같은 것에 대해 계속 말하고 있다
 80  이어지는 이야기다 (앞의 내용이 원인이거나 부연이다)
 50  느슨하게 연결된다 (앞의 이야기에서 흘러왔지만 초점이 옮겨갔다)
 20  다른 이야기다 (앞의 내용과 상관없이 새로 꺼냈다)
  0  완전히 무관하다
```

### 3-4. 룰이 판정한다

```python
CUT_HARD   = 35   # 이 아래면 무조건 자른다
KEEP_SOFT  = 90   # 이 위면 무조건 붙인다
TONE_CUT   = 40   # 회색지대에서만 쓰는 보조 기준
GAP_SOFT   = 30분  # 회색지대에서만 쓰는 보조 기준
```

> **이 값은 앵커에서 역산했다.** 처음에 `CUT_HARD=50` · `KEEP_SOFT=80` 으로 뒀더니
> `case11` 이 통째로 안 잘렸다. 모델이 **거의 앵커 값만 쓰기 때문**이다 — 실측에서
> 100·80·50 만 나왔다. 진짜 경계(2시간 20분 뒤 다툼 시작)가 80 을 받았는데 `KEEP_SOFT=80`
> 이면 무조건 유지로 빠진다.
>
> 앵커를 다시 보면 **"80 = 이어지는 이야기"는 유지 근거가 아니다.** 이어진다는 것과 같은
> 대화라는 것은 다르다. 무조건 유지할 것은 `100`(같은 것) 뿐이고, 무조건 자를 것은
> `20`(다른 이야기) 이하뿐이다. 그래서 임계값은 **앵커 사이에** 놓는다.
>
>     100 ──┐ KEEP_SOFT=90        무조건 유지
>      80   │ 회색지대            시간 공백·말투가 결정
>      50   │
>      20 ──┘ CUT_HARD=35         무조건 자름

```
topic_score >= KEEP_SOFT              → 붙인다
topic_score <  CUT_HARD               → 자른다
그 사이(회색지대)                       → 보조 신호로 결정한다
    시간 공백 >= GAP_SOFT  이거나
    tone_score < TONE_CUT 이면서 same_context == false  → 자른다
    아니면 붙인다
```

**회색지대에서는 붙이는 쪽이 기본값이다.** 잘못 자르면 뒤 단계가 맥락을 잃지만, 안 자르면
분절 전과 같아질 뿐이다. 되돌릴 수 있는 실수를 택한다.

### 3-5. 말투 점수는 단독으로 자르지 않는다

`tone_score` 는 받되 **회색지대의 보조 신호로만** 쓴다. 말투만으로는 절대 자르지 않는다.
근거는 `case7_tone` 이다.

```
101 A  오빠 오늘 몇 시에 와? 저녁 같이 먹으려고 기다리고 있었어
102 B  아 미안 오늘 야근 잡혀서 못 갈 것 같아          ← 화가 난 원인
103 A  또? 지난주에도 그랬잖아
105 A  야 너는 맨날 그런 식이야.
```

호칭이 `오빠` → `야` 로 바뀌고 이모지·ㅋ 가 사라지고 마침표로 끝난다. **말투는 극적으로
바뀌는데 화제는 처음부터 끝까지 저녁 약속 하나다.**

여기서 자르면 활성 세그먼트가 `[105]` 만 남고, 말투 판정에서 **102 가 통째로 빠진다.**
그러면 지금 나오는 대체 문장

> "오늘 못 온다니까 좀 서운했어, 다음엔 미리 말해줘"

가 나올 수 없다. 왜 화가 났는지를 모르니까. 남는 건 "감정이 올라와 있는 것 같아요" 수준의
일반론이고 그건 대체 문장이 아니다. **말투 교정이 자기 발밑을 파는 구조가 된다.**

말투 정보는 자르는 대신 `tone_score` 로 트레이스에 남는다. **말투는 "어디서 자를까"가
아니라 "무엇을 내보낼까"에 쓰는 신호다** (`SUPPRESS_YOUTUBE_WHEN_TONE` 이 이미 그 자리에 있다).

실측에서 이게 그대로 보인다 — `case7` 은 말투 점수가 103 에서 80, 105 에서 90 으로 떨어지는데
화제가 계속 100 이라 안 잘린다.

### 3-6. 비교 기준은 "지금 흐르고 있는 화제"다 — 실측으로 고친 것

전환 직후 실사용에서 **과분절**이 나왔다. 다툼이 계속되는데 발화마다 잘렸다.

```
A: 나는 후룸라이드 타고 싶당
B: 너 다른 남자랑 가봤어?                     화제 20  → 자름 (맞다)
A: 그게 무슨소리야 니가 다른 여자랑 가봤겠지   화제 20  → 또 자름 (틀렸다)
B: 또 그딴소리하네                            화제 20  → 또 자름 (틀렸다)

세그먼트 4개   114~117 | 118~120 | 121~121 | 122~122
```

`그게 무슨소리야…` 는 바로 앞 의심에 대한 **직접 반박**인데 20 을 받았다. 모델이 직전
흐름이 아니라 **원래 화제(놀이공원)와 비교**하고 있었다. 화제가 한 번 바뀐 뒤로는 계속
"원래 얘기가 아니다" 판정이 나온다.

**그리고 이게 경계 흔들림으로도 나타났다.** 발화를 하나 더 넣으면 전체가 재채점되는데,
다툼이 더 길게 보이니 모델이 앞 발화를 다시 100 으로 매겨서 **잘려 있던 게 갑자기 붙었다.**

```
9개일 때 :  121~121 | 122~122     따로
10개일 때:  121~123               합쳐짐
```

사용자가 본 증상은 "합쳐짐"이지만 원인은 과분절 쪽이었다.

프롬프트에 세 가지를 못박아 고쳤다.

- **대화가 처음에 무엇으로 시작했는지는 상관없다.** 화제가 바뀌었으면 바뀐 화제가 새 기준이다
- **응답·반박·되물음은 이어지는 것이다.** 내용이 날카로워도 같은 실랑이면 100 에 가깝다
- **낮은 점수를 연달아 주고 있다면 대개 틀린 것이다** — 기준을 원래 화제에 두고 있는지 확인한다

고친 뒤 3회 연속 동일한 결과가 나오고, 발화를 추가해도 경계가 그대로다.

```
9개 :  114~117 | 118~120 | 121~122      118:20  121:20  나머지 전부 100
10개:  114~117 | 118~120 | 121~123      경계 그대로, 마지막만 붙는다
```

> 낮은 점수가 **화제가 바뀌는 지점에만 하나씩** 찍히는 게 정상이다. 연달아 찍히면 프롬프트를
> 의심한다.

### 3-7. 호출은 요청당 1회로 유지한다

발화마다 LLM 을 부르면 메시지 20개짜리 요청이 20회가 된다. 그래서 **한 번의 호출로 발화별
점수 배열을 받는다.**

```
입력   [1] (20:02) A: 이번 주 토요일에 뭐 하지? 우리 성수 갈까
       [2] (20:04) B: 좋지 카페 가고 싶다 ㅎㅎ
       ...
       [6] (22:30) A: 연락 왜 안 봐

출력   scores: [
         {message_id: 202, same_context: true,  topic_score: 100, tone_score: 100, note: "..."},
         ...
         {message_id: 206, same_context: true,  topic_score: 50,  tone_score: 50,  note: "..."}
       ]
```

첫 발화는 비교 대상이 없으므로 채점하지 않는다.

**점수가 빠지거나 엉뚱한 id 가 섞여도 통째로 버리지 않는다.** 아는 id 만 남기고, 점수가 없는
발화는 "안 자름"으로 넘어간다. 처음에는 전량 대조로 하나라도 어긋나면 조각 전체를 세그먼트
1개로 되돌렸는데, **대화가 길수록 어긋날 확률은 올라가는데 잃는 것도 같이 커지는** 최악의
조합이었다 — 길게 나눠 놓은 경계가 통째로 사라진다.

호출 자체가 실패했을 때만 조각 전체를 1개로 되돌린다 (= 분절 전 동작).
점수를 순서대로 `zip` 하지 않고 **id 로 찾는다.** 하나 빠지면 뒤가 전부 한 칸씩 밀려서
엉뚱한 자리에서 잘리기 때문이다.

배치 방식과 호출 수는 같고, 달라지는 건 **경계 결정이 코드로 나온다는 것**이다.

### 3-8. 시각을 프롬프트에 넣는다

전환 전에는 `[id] sender: content` 만 넣어서 **LLM 이 시간 공백을 아예 못 봤다.** 2시간
50분이 벌어져도 안 보였다 — 3시간 룰 컷 바로 아래 구간이 통째로 사각지대였다.

지금은 `[id] (MM-DD HH:MM) sender: content` 로 넣는다. 다른 프롬프트에서
`text.format_transcript()` 가 하는 일과 같다(데이트 코스가 "밤 10시에 브런치"를 안 넣는
근거가 이것이다).

**회색지대 판정에서 시간 공백이 실제로 결정타 역할을 한다.** `case11` 의 경계 발화는
실행마다 80 또는 50 을 받아 늘 회색으로 떨어지는데, 140분 공백이 매번 같은 결론을 낸다.

## 4. 룰 컷 — 시간 공백

```
GAP_HARD = 3시간   이 이상 벌어지면 LLM 에게 묻지 않고 자른다
```

**실측으로 정한 값이 아니다.** 단일 화제 안 최대 공백이 9분이고 경계가 140분 이상이라 그
사이에 표본이 없다. 룰 컷은 *LLM 없이 확정*이라 **잘못 자르면 고칠 기회조차 없어서**,
넉넉하게 잡고 애매한 것은 전부 채점으로 넘긴다.

**이 컷이 필요한 이유는 실측으로 확인됐다.** LLM 은 화제는 보는데 시간을 못 본다 —
`case4_routine`(사흘치, 공백 1432분·1445분)을 3회 모두 "일상 대화" 한 덩어리로 봤다.
화제가 같으니 LLM 입장에선 틀린 판단이 아니다. 룰 컷이 정확히 이 구멍을 메운다.

> 숫자와 LLM 중 하나를 고르는 문제가 아니라 **서로 다른 구멍을 메우고 있다.**

## 5. 경계 신호로 재보고 버린 것들

시간 공백 말고 룰로 쓸 신호가 있는지 네 가지를 실측했다. **셋이 무너졌다.**

| 방식 | 결과 |
| --- | --- |
| 화제 전환 표지어 | ❌ **반대로 작동** |
| 어휘 겹침 | ❌ **변별력 0** |
| 임베딩 거리 | ❌ **경계에서 오히려 낮음** |
| 시간 공백 | ✅ 유일하게 갈림 |

**표지어** — `case9_date` 는 단일 화제인데 세 번째 메시지가 `근데 만나서 뭐하지?` 로
시작한다. 반대로 실측 스트림의 진짜 경계(`206 연락 왜 안 봐`)에는 표지어가 없다.
사람은 "그건 그렇고"라고 선언하고 화제를 바꾸지 않는다. 그냥 바꾼다.

**어휘 겹침** — 직전 3개와의 2글자 이상 토큰 교집합.

| | 겹치는 단어 수 |
| --- | --- |
| `case9` 같은 화제 안 인접 발화 | 0, 0, 0, 0, 1 |
| 실측 스트림의 진짜 경계 | 0 |

조사가 붙어 `토요일에` 와 `토요일` 이 다른 토큰이고 채팅 문장이 짧다. **같은 화제에서도
0 이면 신호가 아니다.** 게다가 `case4_routine` 은 사흘 내내 같은 인사를 한다 —
**어휘는 거의 같은데 다른 대화 3개다.** 못 잡는 정도가 아니라 반대로 잡는다.

**임베딩 거리** — `retrieve.py` 가 이미 쓰는 `OpenAIEmbeddings` 로 인접 블록 코사인 거리.

```
실측 스트림 (진짜 경계는 206 하나)
  202  0.764   ← 같은 화제인데 최대
  206  0.521   ← 진짜 경계인데 최소 축
```

`case9`(단일 화제) 범위가 0.536~0.689, 경계 있는 스트림이 0.506~0.764로 **분포가 통째로
겹친다.** 짧은 채팅에서 임베딩은 화제보다 **발화 형식**(질문·사과·리액션)을 더 반영한다.

> **결론** — 화제 전환은 문자열이나 벡터 표면에 흔적을 거의 안 남긴다. 표면 특징으로 풀 수
> 있는 문제가 아니라서 **의미 판정(LLM 채점)** 이 필요하다. 룰의 몫은 시간과 임계값이다.

## 6. 어느 세그먼트를 분석하는가

라우팅은 **활성 세그먼트에만** 건다. 1장의 고장은 이 규칙 하나로 고쳐진다 — 데이트
발화(201~205)는 활성이 아니므로 게이트가 아예 그 메시지를 보지 않고, `triggerMessageIds`
도 자동으로 활성 세그먼트 안에 갇힌다.

**맥락과 트리거를 갈라 쓴다.** 이게 6장의 핵심이다.

| | 쓰는 것 | 이유 |
| --- | --- | --- |
| 게이트 · 트리거 id · RAG 질의 · 기억 추출 | **활성 세그먼트만** | 과거 화제가 기능을 발동시키면 안 된다 |
| 말투 판정 프롬프트의 직전 대화 | **맥락(활성 + 부족분)** | 활성이 1개면 장난인지 갈등인지 구분할 수 없다 |
| 말투 기준선(`profile.py`) | **전체 스트림** | 기준선은 표본이 넓을수록 정확하다 |

| 상황 | 처리 |
| --- | --- |
| 활성 세그먼트가 4개 미만 | 앞 세그먼트에서 뒤에서부터 채워 맥락 4개를 확보한다 |
| 세그먼트가 1개다 | 분절 전과 완전히 같다 |

**규격서 6장의 "여러 기능 동시 발동"을 어기지 않는다.** 제한하는 것은 *기능 개수*가 아니라
*화제*다.

## 7. 화제 라벨을 만들지 않는다

배치 방식일 때는 세그먼트마다 `topic`(`"주말 계획"`) · `mood` 라벨이 붙었다.
**점수 방식에서는 만들지 않는다.**

만들 수가 없다 — 경계를 룰이 **나중에** 정하므로, 채점 시점의 LLM 은 세그먼트가 어디서
어디까지인지 모른다. 억지로 받아내려면 발화마다 라벨을 달게 해야 하는데 그럴 이유가 없다.

**안 만드는 게 오히려 안전하다.**

> ⚠️ LLM 이 라벨에 `"권태기 조짐"`, `"요즘 대화가 줄어든 것에 대한 다툼"` 같은 문자열을
> 붙일 수 있다. 이 프로젝트의 **절대 제약** 정면 위반이다. `filter.py` 는 `AiResult` 의
> 화면 문자열만 검사하므로 라벨은 걸러지지 않는다. 라벨 자체가 없으면 이 위험이 사라진다.

디버깅 정보는 점수와 `note` 가 대신하고, 그쪽이 더 정밀하다 — "왜 이 세그먼트인가"가
아니라 **"왜 여기서 잘렸는가"**를 알려주기 때문이다. `note` 에도 관계 상태를 쓰지 못하게
프롬프트로 막아뒀고, 트레이스 밖으로 나가지 않는다.

**`tone_score` 를 규격서 11장의 감정 분석(`emotionAnalyses`)과 섞지 않는다.** 그쪽은 명세가
없는 별도 기능이고 화면에 나간다. `tone_score` 는 절대값이 아니라 **직전 대비 연속성**이라
애초에 다른 값이다.

## 9. 비용과 레이턴시

`devui` 가 단계별로 계측한다 (`worker/llm.py` 의 `USAGE.records` — 호출마다 출력 스키마
이름·시간·토큰을 남긴다).

| 케이스 | 총 소요 | LLM | 외부 API·룰 | 그중 분절 호출 |
| --- | --- | --- | --- | --- |
| `case11_mixed` (8개, 결과 1건) | 7.0초 | 4회 5.9초 | 1.1초 | 2.0초 |
| `case9_date` (6개, 카카오 3회) | 8.3~8.7초 | 4회 6.6~7.4초 | 1.2~1.7초 | 1.5~1.7초 |

### 근거 문구(`note`)를 받지 않는다 — 분절 호출 절반

처음에는 발화마다 `note` 를 한 줄씩 받았다. 8개짜리 대화면 근거 문장을 7개 생성하느라
출력이 292 토큰이 되고 **분절 호출이 4.0초**였다.

빼고 두 케이스를 5회씩 끝단으로 돌렸다.

| | 분절 호출 | 경계 정확도 |
| --- | --- | --- |
| `note` 있음 | 4.02초 / 3.84초 | 5/5 |
| **`note` 없음** | **2.31초 / 2.64초** | **5/5** |

**경계가 완전히 같다.** 잃는 것은 "왜 그 점수인지"뿐이고, **"왜 잘렸는지"는 점수·임계값·
공백으로 이미 계산되어 화면에 나온다** — `note` 는 2차 정보였다.

> ⚠️ **"점수가 높을 때만 `note` 를 생략" 하는 절충은 하면 안 된다.** 실측에서 모델이 쉬운
> 길로 쏠려 **점수를 전부 100 으로 매기고 경계를 통째로 놓쳤다.** 조건부로 일을 줄여주면
> 그 조건 쪽으로 답이 쏠린다. 지우려면 완전히 지운다.

### 외부 API 를 동시에 부른다

카카오 검색은 서로 독립인데 검색어마다 순차로 돌고 있었다. **실측 0.75초 → 0.20초.**
유튜브의 `commentThreads`(후보마다 1회)도 같은 이유로 동시에 부른다.

지역명이 없을 때만 순차가 남는다 — **첫 장소가 코스의 중심**이라 그것만 먼저 확정해야
한다(`build_course`). 첫 검색이 비어서 중심을 못 잡으면 원래대로 순차로 돈다.

`case9` 의 외부 API·룰 구간이 3.2초 → 1.2~1.7초로 줄었다 (RAG 임베딩 호출 포함).

병렬화가 안 되는 곳: **모든 후보가 분절 결과를 기다린다.** 후보 기능끼리의 병렬 실행은
`SUPPRESS_YOUTUBE_WHEN_TONE` 때문에 유튜브가 말투 결과에 의존해서, 말투·데이트만 묶을 수
있다. 타임아웃 기준이 정해진 뒤에 한다 (`worker-tasks` 14단계).

### 그래도 순증이 아니다

1장 실측 기준으로 데이트 코스가 미발동하면서 LLM 2회와 카카오 2회가 통째로 빠진다 —
**1회를 더하고 3회를 빼서 순감이다.**

```
분절 전   extract + tone_judge + tone_suggest + plan_date + write_reason  = 5회 + 카카오 2회
분절 후   segment + extract + tone_judge + tone_suggest                   = 4회 + 카카오 0회
```

## 12. 검증

### 12-1. 점수 보정부터 잰다 (1순위)

임계값을 정하려면 점수가 안정적인지부터 알아야 한다. **같은 대화를 5회씩 채점해 발화별
점수의 분산을 본다.** 분산이 크면 임계값 방식 자체가 성립하지 않으므로, 그때는 점수를
버리고 이산 등급(`same` / `related` / `shifted` / `unrelated`)으로 내린다.

### 12-2. 임계값을 점수 분포에서 정한다

경계인 곳과 아닌 곳의 점수 분포를 그려서 겹치는 구간을 회색지대로 잡는다.
데이터는 `data/eval/msd_sample.jsonl`(실제 한국어 대화 2000건)을 쓴다.

- **과분절률** — 단일 세션(한 대화)이 세그먼트 1개로 나오는가
- **경계 탐지** — 다른 주제 대화 둘을 **30분 간격**으로 이어붙인다. 3시간 컷 미만이라
  룰이 안 걸리고 채점만으로 찾는지 격리해서 볼 수 있다

> ⚠️ **시간 공백 임계값은 이 데이터로 검증되지 않는다.** 빌더가 세션 내 `sentAt` 을 1~5분
> 랜덤으로 **생성**한다(원본에 시각이 없다). `gapDays` 만 원문에서 읽은 진짜 값인데 일
> 단위라 3시간 컷은 무조건 걸린다. 임계값은 실서비스 로그가 쌓여야 정할 수 있다.

### 12-3. 픽스처 회귀

| | 기대 |
| --- | --- |
| `case11_mixed` | 세그먼트 2개(`201~205` / `206~208`), **데이트 코스 미발동**, 말투 교정만 |
| `case7_tone` | **1개** — 말투가 극변해도 안 쪼갠다 (3-5) |
| `case9_date` · `case8_banter` · `case10_concern` | 각 1개, 결과 불변 |
| `case4_routine` | **룰 컷 3개** — LLM 은 한 덩어리로 본다 (4장) |

**점수 방식으로 전부 통과했다.** `case7` 이 특히 확인이 되는데 — 말투 점수가 103 에서 80,
105 에서 90 으로 떨어지는데 화제가 계속 100 이라 안 잘린다. 말투 단독 절단 금지(3-5)가
실제로 작동하는 것이 점수로 보인다.
